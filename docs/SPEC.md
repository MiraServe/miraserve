# MiraServe — Architecture Specification & Roadmap

> Reference specification for MiraServe, synced through Milestone 5 (Packaging, Release Supply Chain & Audit Readiness).

## 1. Product Pillars

1. **Memory-Safe, Hardened Core:** Every MiraServe crate that ships in the binary (15 of 16 workspace members) enforces `#![forbid(unsafe_code)]` and a zero-panic runtime policy (`miraserve-alloc-tests`, the tests-only 16th member, holds one audited `unsafe impl GlobalAlloc`); third-party dependencies — including the vendored `h2` crate and the `aws-lc-rs` cryptography library — contain `unsafe` Rust or C/assembly (`rustls`, `aws-lc-rs`, `hyper`, `quinn`, `h3`, `cap-std`, `wasmtime`).
2. **Modern HTTPS by Default:** TLS 1.3 only by default, `X25519MLKEM768` post-quantum hybrid KEX prioritized, automatic ACME v2 + short-lived certs + RFC 9773 ARI, ECH (RFC 9849) ready, and optional split-privilege `miraserve-keyd` signing daemon.
3. **Transition Bridge for Today's Web:** Pure-Rust async FastCGI client for isolated WordPress/PHP-FPM, `wordpress-hardened` security preset, opt-in `compat-tls-1-2`, and `miraserve import` converters for Nginx, Caddy, Apache, and OpenLiteSpeed.
4. **AI-Native Future Web:**
   - **Atomic Self-Updating AI Website Publisher (`miraserve-publish`):** Signed immutable site bundles, pre-flight secret/CSP checks, zero-downtime atomic swap, rollback to a retained release, and MCP publishing tools.
   - **RFC 9421 / Web Bot Auth:** Cryptographic agent identity verification.
   - **MCP Security Gateway:** OAuth RFC 9728 metadata, JWT validation, JSON-RPC tool-level RBAC, redacted audit logs.
   - **LLM Streaming & Content Negotiation:** Zero-buffer SSE flushing, `llms.txt`, and `Accept: text/markdown`.
5. **Cross-Platform Deployment:** Linux-first hardened production (Landlock, seccomp-bpf, systemd, distroless OCI), macOS Homebrew formula + `launchd`, Windows single `.exe` + Windows Service.

## 3. Milestones

- **M0 (Foundation — Weeks 1–2):** Workspace + strict lints, `deny.toml`, `THREAT_MODEL.md`, `miraserve-config` KDL schema & validator, `miraserve check` CLI, cross-platform tests & CI.
- **M1 (Secure Core MVP — Weeks 3–10):** TLS 1.3 PQC (`X25519MLKEM768`), auto-ACME + dev TLS, HTTP/1.1 + HTTP/2 + HTTP/3, `cap-std` static server, reverse proxy (SSE/WS), graceful reload.
- **M2 (Hardening & Transition Bridge — Weeks 11–18):** Anti-smuggling, H2/H3 flood defenses, GCRA rate limiter, `wordpress-hardened` preset, Landlock/seccomp, FastCGI client (WordPress test harness), `miraserve import` (Nginx/Caddy/Apache/OLS).
- **M3 (AI-Native Edge & Publish — Weeks 19–28):** `miraserve-publish` (signed atomic deployments + MCP publisher + rollback), RFC 9421 Web Bot Auth, MCP Security Gateway (OAuth RFC 9728 + tool RBAC), `llms.txt` / Markdown negotiation.
- **M4 (WASM, Split-Key & ECH — Weeks 29–36):** `miraserve-wasm` (`wasmtime` `wasi:http`), `miraserve-keyd` split-privilege signing daemon, ECH (RFC 9849) rotation, OTLP/Prometheus telemetry.
- **M5 (Packaging, Audit & v1.0 — Complete):** `miraserve service` (`systemd`, `systemd-keyd`, `launchd`, Windows Scheduled Task), Homebrew formula, WinGet manifest, Linux `.deb`/`.rpm` (`nFPM`) + rootless distroless OCI `Containerfile`, SHA-pinned SLSA Build Level 2 + Cosign + CycloneDX SBOM release pipeline, smoke-baseline & Linux benchmark methodology, deployment/migration guides, and multi-auditor security audit prep & verification record.

## 4. Security Defaults

- **Static script source & secret/backup protection (`R6-STA-1`, `R7-STA-1`, `R7-STA-2`, `R7-STA-3`):** `miraserve-static` refuses static serving (returns `404`) by default for:
  - Server-side script extensions `.php`, `.phtml`, `.phar`, `.phps`, `.php5`, `.php7`, `.php8`, `.pht`, `.phpt`, and `.inc` — in **any** non-first dot-separated filename segment, including case variants, backup/editor/archive suffixes (`wp-config.php.bak`, `x.php~`, `x.php_`, `x.php.swp`, `x.php.orig`, `x.php.1`, `x.php.txt`, `x.php.gz.bak`, `x.inc.bak`), Windows trailing-space/dot and NTFS Alternate Data Stream spellings (`x.php%20`, `x.php::$DATA`), directory index candidates, `try-files` matches, and multi-hop symlinks (up to 8 hops, failing closed on deeper chains or loops). `.inc` is intentionally denied with no static override to prevent PHP include-file source disclosure; serve downloadable text under a non-script extension (e.g. `.txt`).
  - Sensitive private keys, key stores, database dumps, editor/backup files, and PHP dependency manifests: `*~`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, `*.jks`, `*.kdbx`, `*.sql`, `*.sqlite`, `*.sqlite3`, `*.bak`, `*.swp`, `*.swo`, `*.orig`, `*.old`, `*.save`, `composer.json`, and `composer.lock` (including `.gz`/`.br`/`.zst` compressed copies and symlink targets).
  - This safety floor is always active on static routes and cannot be disabled via configuration; execute PHP scripts via an explicit `fastcgi-pass` route.
- **Relative config paths & config-in-docroot refusal (`R6-CFG-1`, `R7-CFG-1`, `R7-CFG-2`):** When loading a configuration file from disk (`miraserve check` / `miraserve run` / `miraserve reload`), relative `root` and `ai-publish.storage` paths (without `..`) resolve against the configuration file's absolute directory before sensitive-root validation. If the configuration path is a symlink, relative paths resolve against the canonical target file's parent directory. Any `site.root` or `route.root` equal to or an ancestor of the configuration directory (such as `root "."`) is rejected with `E202` so the `.kdl` config file itself can never be served over HTTP. Standard input (`-`) and in-memory parses require absolute paths.
- **Leading and trailing whitespace in KDL filesystem paths (0.1.8 — behaviour change vs. 0.1.7):** At configuration load, MiraServe rejects any in-scope host-filesystem path value whose decoded KDL text starts or ends with Unicode whitespace (`path != path.trim()`, covering ASCII space, tab, CR/LF, NBSP `U+00A0`, ideographic space `U+3000`, etc.) with the white-space `E202`, naming the directive (and, for site or route directives, its site or route) and identifying the offending Unicode code point(s) (with semantic JSON `path` and source location in `miraserve check --format json`). E202 is emitted for a padded in-scope value when the value is read AND its enclosing site or route is retained by the loader. This applies to `server.acme-webroot`, each `server.allow-docroot`, `server.tls.{cert,key,client-ca,keyd-socket}`, each `server.sandbox.{read-tree,socket-tree}`, `site.root`, `site.owner-dir`, `site.basic-auth`, `site.tls.{cert,key,client-ca}`, `site.bot-auth.agent-keys-file`, `site.ai-publish.{storage,require-signature,jwt-public-key}`, each `site.error-pages` `page` path, `site.route.root`, `site.route.fastcgi-pass` (`unix:` form), `site.route.wasm-plugin`, `site.route.mcp-gateway.jwt-public-key`, and `site.route.reverse-proxy.upstream-tls.{ca-cert,client-cert,client-key}`. For recognized `ed25519:` and `unix:` file forms, both outer padding and leading/trailing whitespace on the pathname after the prefix are rejected; for `server.tls.keyd-socket`, outer endpoint padding and `unix:` pathname padding are rejected while existing TCP grammar checks remain unchanged. For the three file-relative directory directives (`site.root`, `route.root`, `site.ai-publish.storage`), if joining a relative value against the config file's directory exposes trailing whitespace in the resolved directory name (for example `"app /."` or `"app /"`), configuration load likewise rejects it with `E202` against the original directive when the enclosing site or route is retained. A configuration rejected at load gets no post-load filesystem checks (`--fs`, `--trusted-paths`, `--writable-set`, or reload filesystem preflight) until the load errors are corrected, and each command shows warnings for a failed load exactly as it does for any other load error. `miraserve check`, `miraserve run`, and `miraserve reload --config` preflight refuse a rejected configuration and display the load errors (including each emitted `E202`); `miraserve keyd --config` and config-backed `miraserve publish` (`deploy`, `rollback`, `resign`) fail the load and print only the validation error-count summary; ordinary `miraserve service generate --config` validates when it reads the KDL to infer the drain timeout or `ProtectHome`, discards a validation error, and uses defaults (while `--print-writable-set` returns before reading the KDL); `miraserve-config` loaders and `ConfigStore` reloads return `ConfigError::Validation`, and `RunningServer` reloads return `CoreError::Config(ConfigError::Validation { .. })`. Internal spaces (such as `C:/Program Files/...`), `index` basenames, `try-files` templates, URI paths, inline `miraserve-ed25519-pub:` keys, route-level `basic-auth` (`E311`), and CLI path flags are unchanged.
- **Default-deny document root confinement (`R6-SBX-1`, `R7-SBX-1`, `R7-SBX-2`, Section 5):** All single-segment top-level directories (`/srv`, `/opt`, `/mnt`, `/data`, `/System`, `/Volumes`, etc.), hidden dot-directory segments, OS credential/kernel/config trees (`/etc`, `/root`, `/proc`, `/sys`, `/dev`, `/boot`, `/Library/Keychains`, `/System`, `/usr/lib/ssl`, `/var/backups`, `/var/mail`, `/var/spool`, `/run/secrets`, `/run/credentials`), and MiraServe's own config/state/runtime paths on any prefix (`/var/lib/miraserve/**`, `/opt/homebrew/var/lib/miraserve/**`, `/opt/homebrew/etc/miraserve/**`, `/usr/local/var/lib/miraserve/**`, `/private/var/lib/miraserve/**`, `/run/miraserve*`) are unconditionally forbidden as HTTP document roots. All other paths under `/var/lib`, `/var/log`, and `/run` are denied by default and may only be opened for specific subdirectories via `server { allow-docroot "/var/lib/my-app/public" }`. Both startup and live `reload` (as well as `miraserve check --fs`) enforce identical checks against symlink targets, the running process's effective ACME state directory, TLS private keys, `ai-publish.storage`, and the config directory.
- **Publish preflight markup scanner bounds (`no-inline-scripts` / `csp-valid`):** Active HTML, XHTML, SVG, and XML files are parsed with `html5ever` and `roxmltree` under bounded anti-DoS limits: **2 MiB** per active markup file, **200,000** DOM nodes, **512** element nesting depth, **1,024** attributes per start tag, and **4 MiB** total expanded attribute memory per document. External `<script>` URLs, `<base href>`, `xml:base`, and `<script type="importmap">` / `<script type="speculationrules">` URL targets must resolve strictly same-origin via WHATWG URL parsing. Benign HTML5 tree-recovery constructs (snippets without DOCTYPE, legacy `<!DOCTYPE html5>`, `<head><noscript><img>`, missing whitespace between attributes, missing entity semicolons, `--!>` comment closers, inert `<script type="text/template; ...">` / `application/json`, and passive SVG `<image>` / `<feImage>` data URIs) are accepted while all parsed elements and merged attributes remain strictly validated.
- **Connection caps, front proxies, and memory bounds (`server.limits` / `rate-limit`):**
  - `max-connections` defaults to `16384`; `max-connections-per-ip` defaults to `128` per IPv4 `/32` or IPv6 `/64`, with an aggregate IPv6 `/48` cap of `ipv6-prefix-conn-multiplier * max-connections-per-ip` (default multiplier `4`, configurable `1..=1000` for large campus/NAT `/48` networks).
- **Event loops (`server { workers ... }`, 0.1.5, Linux):** `workers "shared"` (the default, omitted from `--dump-normalized`) runs every connection on one multi-thread runtime with no worker threads and no `SO_REUSEPORT` sockets (see the opt-in off-path cost list below for the small shared-runtime hooks that remain when off). With `workers` set to a number or `"auto"`, each `reverse-proxy` route builds its own request client and its own HTTP/1.1 upgrade and `preserve-host` client per worker, and an in-range worker uses its own pair. `workers "auto"` chooses a thread count from available parallelism (`std::thread::available_parallelism`) and **does not pin threads to CPU cores**; `workers <N>` starts `N` (1 to 256) worker threads. Each worker thread runs a single-thread event loop with its own `SO_REUSEPORT` listening socket (requested listen backlog **1,024 per socket**, subject to kernel limits); a connection stays on the thread that accepted it. For **`reverse-proxy` routes**, each route allocates one request client (`pool_idle_timeout` 60 s) and one HTTP/1.1 upgrade/`preserve-host` client (`pool_idle_timeout` 30 s) per worker loop (`0..N`) in addition to the shared clients used by shared-runtime traffic (HTTP/3, plain-HTTP `http "serve"` listeners), active health probes, blocking-pool work, or an out-of-range worker index after a reload that lowers `workers`; requests on worker `i` use pool `i` so both downstream and upstream connection tasks stay on worker `i`'s single-thread runtime without cross-core wake-ups (`workers "shared"` allocates zero per-worker pools and keeps the single shared pool unchanged; `BackendPool`, active/passive health state, load-balancing state, and the effective connect timeout remain shared across all pools of a route). **Upstream connection-count consequence:** `hyper-util`'s per-host idle connection limit (`pool_max_idle_per_host`) is unset (unbounded, `usize::MAX`) per pool today, and the configured `60 s` (request client) / `30 s` (upgrade/`preserve-host` client) idle ages are **checkout-only** (`pool_timer` is unset, so idle sockets are checked for expiry only when reached on checkout rather than reaped by a background timer); with `N` workers idle HTTP/1.1 keep-alive connections to a single upstream can therefore grow up to **`N` times** the single-pool count (plus the shared pool when shared-runtime traffic or active health probes also reach that upstream) and linger beyond 60 s / 30 s while idle. For upstream HTTP/2, one multiplexed connection per active request pool describes **steady-state reuse** — up to **`N`** multiplexed HTTP/2 connections per upstream across the worker loops (plus 1 on the shared pool if used), though concurrent TCP/TLS handshakes can precede ALPN selection before a shared HTTP/2 connection is established; operators sizing an upstream's connection limit must multiply by the worker count `N`. Because Linux gates `SO_REUSEPORT` socket-group membership by effective UID in the network namespace — any other process under the same UID can join the group and receive new connections, regardless of PID-file locks — `workers` assumes MiraServe runs under a **dedicated service user** (as in the packaged systemd unit). Each worker loop's blocking thread pool is capped at `max(8, 256 / workers)` threads with a 10 s idle keep-alive: up to 256 worker blocking threads in total for 1 to 32 workers, and **`8 x workers` above 32 workers** (for example 512 at 64 workers and 2,048 at 256 workers — 256 is **not** a process-wide ceiling above 32 workers), in addition to the shared runtime's blocking pool, which is unchanged. At most 8 buffered proxy-compression jobs handed off worker loops (or in-task HTTP/2 streams) may be queued or running in blocking pools at a time, process-wide; frames are consumed into one contiguous buffer (zero-copy for single-frame bodies) before awaiting a permit so no duplicate copy is held across the await, and waiters are bounded process-wide by a **32 MiB** waiter byte budget (combined with at most 8 × 4 MiB active jobs = 64 MiB total cap on **waiting and active input payloads only**, excluding body collection, encoder output buffers, allocator overhead, and downstream transport bodies; when saturated while all 8 permits are busy, requests that accept `identity` skip the wait and return uncompressed immediately with `Vary: Accept-Encoding`, while requests that exclude `identity` via `identity;q=0` or `*;q=0` without an explicit `identity` of `q > 0` compress incrementally over the buffered body via `YieldingStreamingCompressedBody` using the highest-weighted streamable coding in `{br, gzip}` (ties `br > gzip`) with no permit and no extra waiting buffer beyond the body itself — or preserve the upstream response uncompressed with `Vary: Accept-Encoding` if no streamable coding is acceptable, e.g. only `zstd`; dropping a waiting request frees its buffer and waiter reservation immediately). `workers` assumes **local document roots**: on a worker loop thread, static lookups run inline only via non-blocking `openat2(RESOLVE_CACHED)` and non-syncing `statx(AT_EMPTY_PATH | AT_STATX_DONT_SYNC, STATX_BASIC_STATS | STATX_MNT_ID)` (never falling back inline to the blocking `openat` walk or blocking `fstat`), large files and byte ranges (`> 256 KiB`) never `seek` and stream lazily on the blocking pool in batched positional reads (see below), and small-file reads (`<= 256 KiB`) run inline via positional `preadv2(RWF_NOWAIT)` only when: (a) the kernel release is in **Linux 5.9–6.11** (where `RWF_NOWAIT` carries `IOCB_NOIO` so the generic buffered read starts no readahead in the caller; read once from `/proc/sys/kernel/osrelease` before sandboxing — unreadable `/proc` or any release without a parseable `major.minor` prefix in `5.9`–`6.11` counts as outside; a vendor kernel backporting the 6.12 change under an in-range number is not recognised), (b) the document root's per-root `RootReadPolicy` (evaluated off the serving path in `StaticServer::open` at startup, reload, and `ai-publish` activation via `fstatvfs` `ST_RDONLY | ST_NOATIME` and `statx(STATX_MNT_ID)`, requiring Linux 5.8+; skipped — marking the root unsuitable with v0.1.4's exact root-open calls — whenever the warmed kernel release is outside Linux 5.9–6.11, once `openat2`/`RESOLVE_CACHED` is already latched unavailable, or in `CompiledRouter` when neither dedicated `workers` nor Linux 5.12–6.11 HTTP/2 is configured; unknown counts as unsuitable; never probed on a request and refreshed only on reload — a live remount without a reload keeps the prior answer) reports an `atime_free` mount and has not latched a `preadv2(RWF_NOWAIT)` refusal (`EOPNOTSUPP`/`EINVAL`/`ENOSYS`/`EPERM`, e.g. `overlayfs`/`tmpfs`), and (c) the selected file's `statx` `mount_id` equals the root's `mount_id` (nested mounts can carry different mount flags). Anything else (unsuitable root, unknown/mismatched `mount_id`, prior refusal, zero-byte/short/`EAGAIN` read, or outside kernel range) skips or stops inline reading and hands the retained descriptor to the worker's blocking pool (with 0 buffer allocation and 0 `preadv2` syscall once unsuitable or refused); remaining P2 residuals on supported `noatime`/read-only local roots are `fanotify` permission listeners, filesystem-specific waits (such as an ext4 DAX extent lookup), and a live remount between reloads. Under a systemd unit that sets `RestrictSUIDSGID=yes` (including the packaged default), systemd's seccomp filter answers `ENOSYS` to `openat2`, so worker loops cannot perform inline lookups and fall back to their blocking pool until the unit is generated with `miraserve service generate --target systemd --allow-openat2` (`miraserve check` and startup emit a one-time notice when `openat2` is refused). When a selected small-file read returns `WouldBlock` (unsuitable root, `mount_id` mismatch, `EAGAIN`, short read, refusal, or outside the kernel range), or when cold on-the-fly compression is needed, the worker carries the **selected descriptor and the original request headers (including `Range` and `If-Range`)** to its capped blocking pool, where post-dequeue authorization applies the retained-credential predicate (`authorize_retained_fd`, denying any live generation's known credential at any link count) and `Range` and `If-Range` are evaluated AGAIN from the original headers (the worker evaluates them once before the read that can return `WouldBlock`; its result is not carried across the hand-off); the file's metadata is read again at that point exactly when credential protection is active for the process (`any_secret_files()`: the serving generation lists a credential file, or any generation has published one since the process started — that process-wide flag stays set after the last such generation is gone) — otherwise the second evaluation uses the length and validators taken when the file was selected, so after an in-place modification of that inode in between they can describe the file as it was at selection on both single-pass and ordinary direct paths (cached and uncached); `Unknown` classifications before selection (or on an undecidable precompressed sibling) and deferred paths (`RetentionPolicy::DEFERRED`: authored `.md`, HTML-to-Markdown conversion, and serving generations carrying `UNIDENTIFIED_CREDENTIAL`) resolve afresh on the worker's blocking pool (with single-pass script-vs-static decisions still preserved across sibling `Unknown` recovery). On a network or FUSE file system `openat2` itself can wait. Because all worker loops share one `HttpEngine`, the inline slow-lookup circuit breaker (`inline_paused_until_ms` / `inline_slow_score`, updated via atomic CAS / `fetch_max` with a **5 s** `INLINE_PAUSE`) is shared **per opened `StaticServer` and its clones** across all worker loops (slow lookups on any worker accumulate together and pause inline serving across every worker sharing that server, while separately opened routes pointing at the same directory get distinct breakers as in 0.1.4, and `file-cache` hits remain in-memory and do not affect the breaker). The `acme-webroot` token file lookup and 4 KiB read offload to the blocking pool on worker loops (and on in-task HTTP/2 streams). Startup rollback after a worker initialization failure joins already-started worker threads under the same bounded 2 s join deadline (`WORKER_SHUTDOWN_JOIN_GRACE`) as normal shutdown. There is still one process, one pid file and one status file; every limit, budget and connection count is process-wide; Landlock is applied on every worker loop thread and its blocking threads; the HTTP redirect listener and HTTP/3 stay on the shared runtime. When `key-isolation "split-daemon"` (`miraserve-keyd`) is configured, `workers` is ignored with a startup warning and the shared runtime is used. Changing `workers` on reload logs a warning and reports `server.workers` in `restart_required` (taking effect on restart, and clearing if reverted). Other systems use the shared runtime whatever is set.
  - **Large FastCGI answers (0.1.2):** an answer up to 32 MiB is read whole before it is sent. A larger one (a download made by PHP) is streamed: the backend worker is held until the client has taken it. `max-streamed-answers-per-ip` (default `8`, 1 to 10000) is how many such answers one IPv4 address or IPv6 `/64` may have at once, and `max-streamed-answers-per-backend` (default `4`, 1 to 10000) how many one FastCGI backend may have for all clients together: keep it below the pool's worker count (`pm.max_children`), or downloads can occupy every worker. A backend whose pool has another size sets its own number on its route: `fastcgi-pass "unix:/run/php/site.sock" max-streamed-answers=2`. One more gets 502, which is what every answer of that size got before 0.1.2 (the script has already run, so no retry is suggested), and a log line naming the setting. The limits of a reloaded configuration apply when the reload is committed. A `Content-Length` the script sets is passed on for a streamed answer and enforced.
  - **Opt-in static file cache (`site.file-cache`, `server.limits.file-cache-bytes`, 0.1.5):** off by default, so sites that do not opt in see every filesystem change on the very next request. **Kept guarantees when both opt-in 0.1.5 features (`file-cache` and `workers`) are off:** on the Linux link-free fast path (`openat2` / `fast_open_walk`), uncached static `GET`/`HEAD` requests perform the exact same filesystem calls as 0.1.4 (Linux kernel-call table unchanged: direct file 1 open / 1 status read, plain index 2 / 2, script-routed index 2 / 2); on the full resolver slow path (paths involving symlinks on Linux/Android, and all full lookups on macOS/Windows/other platforms), requests run `v0.1.4`'s resolver unchanged: its name walk of the link chain (up to 8 hops, with the dotfile and forbidden-extension checks on the names it walks) followed by its confined open of the original path. On **stable trees** (no concurrent link switch or ancestor mutation), both fast and full paths produce HTTP responses, headers, redirects, error kinds, and access-log lines identical to 0.1.4 (`cac718b`), with zero cache-clock reads, zero cache shard locks or sweeps, zero cache lookup or admission calls, zero worker threads or `SO_REUSEPORT` sockets, no growth in the per-request boxed pipeline futures (cache-enabled branches and worker-only buffered proxy compression are boxed out of the off path), and no growth in the shared-runtime `StreamingCompressedBody` wrapper. **Dropped claim & remaining off-path costs:** MiraServe does **not** claim that the all-off process or request path is instruction-, allocation-, control-path-, or metrics-output-identical to 0.1.4; the remaining costs when both features are off are: (1) one cached `site.has_file_cache` boolean check per request at site dispatch (plus one cached `router.has_file_cache` check only on requests matching a configured `acme-webroot` HTTP-01 challenge path, `Option` checks in `StaticServer::set_secret_files`/`set_precompressed` on `ai-publish` active servers, and one or two `file_cache.is_some()` checks on direct public `StaticServer` callers outside the router's `*_no_cache` entry points — for example `serve_canonical` checks once in `serve_inner`, while `serve_canonical_looked_up` checks once to decide whether to unpack `FillStart` and again in `serve_inner`); (2) an OS-thread-local boolean read (`is_worker_loop_thread`) on the shared runtime inside `inline_mode()` (when the inline breaker allows inline work), FastCGI script-existence / non-read `try-files` existence helpers, and eligible proxy compression (without touching worker-only paths or initializing the lazy 8-permit worker compression semaphore); (3) engine startup allocates an empty `FileCacheBudget` and an 8 KiB striped counter table (256 atomics) and scans site eligibility, reload commit stores `file-cache-bytes` into that budget and nonempty credential publication advances the credential epoch, metrics scrapes sum those 256 counters and emit the four `miraserve_file_cache_events_total` / `miraserve.file_cache.events` series even when all are `0`, server startup creates a `workers_exit` watch channel and shared shutdown sends on it after the empty-worker check, `LimitsConfig` carries an 8-byte `file_cache_bytes` field (omitted from `--dump-normalized` when equal to the `64MiB` default so existing v0.1.2–v0.1.4 normalized dumps remain byte-identical), and `StaticServer` / `Lookup` carry fixed-size `None` optional fields. A site may opt in with `file-cache "<duration>"` (`100ms` to `60s`; absent or `"off"` disables it), bounded process-wide across all sites, worker loops, and reload generations by `server.limits.file-cache-bytes` (default `"64MiB"`, maximum `"1GiB"`, `0` disables the cache everywhere at once). `miraserve check` lists sites with `file-cache` and their window as an informational note (not a warning).
    - **Guarantee, clock, descriptor retention, and breaker (0.1.5):** each cached entry has a fixed deadline anchored once before the first filesystem access made for the request (`lookup_started + window`, covering rewrite file checks, router directory-index probes, and blocking resolvers alike; where both filesystem rewrites and a FastCGI index probe sample, the earlier sample wins; any request that made an earlier filesystem access before a fill timestamp was sampled — such as an ACME webroot lookup that missed and fell through to the site — or cannot carry a valid cache-owned timestamp does not admit, while fresh hits remain unaffected and the ACME check still runs before static dispatch), never extended by hits. Entry freshness is decided using a clock sample taken while holding the shard lock on both read and replacement paths. On Linux the cache clock uses `CLOCK_BOOTTIME` (counting suspended time); on other systems it uses `std::time::Instant`, where the elapsed-time bound assumes the system does not suspend. Inside the window, matching requests are answered from memory with no filesystem calls (no open, stat, read, index probe, or `try-files` probe) and no inline circuit-breaker accounting (hits neither cool nor heat the breaker and continue to serve from memory even while the breaker is paused). `FileCache` stores only immutable in-memory bytes and headers and never retains file or directory descriptors after a fill finishes reading. On Linux, cache fills follow the 0.1.4 single-pass descriptor-retention and combined-breaker rules: an in-flight fill retains the regular file descriptor it selected (including across cold-compression pool hand-off, with post-dequeue reauthorization) even if replaced on disk while filling, times its combined inline operation as one breaker interval, and anchors its expiry to the pre-lookup `FillStart`. Once the deadline passes, the next request takes the normal filesystem path in full and refills, so any change (content, deletion, rename, permissions such as `chmod 000`, ownership, symlink retarget, or parent directory rename/unreadable) is **visible at the latest one window after the change**, regardless of traffic.
    - **What is cached (0.1.5):** `GET` and `HEAD` (sharing an entry; `200 OK` `GET` fills, `HEAD` and conditional `304` hit and evaluate `If-None-Match` / `If-Modified-Since` fresh via the same conditional evaluator); complete regular files up to the in-memory threshold (`256 KiB`, requiring the uncompressed base file's size observed when selecting any precompressed sibling — never re-queried by path — as well as the selected sibling and final body to all be within `256 KiB`); identity, enabled precompressed sibling (`.zst`/`.br`/`.gz`, strictly honoring the site or route `precompressed` policy, which defaults to `"off"`, and allocating a fresh cache namespace on policy mutation or reload), or on-the-fly compressed representations keyed per negotiated `Accept-Encoding` outcome on static routes and eligible `try-files` routes (with the exact candidate list, script-extension list, and script-owner predicate bound to the cache namespace). All pre-static checks (routing, access rules, `basic-auth`, rate limits, WAF/presets, method checks, conditional and range evaluation, and fresh `Date` / request ID) and post-handler configurable `headers` rules (including status-conditioned `status=` rules) run on every request, and no extra response header is emitted. Cached `try-files` fallback entries record their expanded fallback candidate path (charged to `file-cache-bytes`) so cache hits preserve 0.1.4 fallback route `headers` ownership (`TryFilesOutcome::FallbackResponse`); refused candidates (`400 Bad Request`) are never cached and keep the originating route's `headers` rules.
    - **What is not cached (0.1.5):** anything refused by credential-file protection: every credential publication (including during `prepare_reload`) runs under a serialized odd/even publication boundary on `CREDENTIAL_EPOCH` — advancing the epoch to an odd in-progress value *before* mutating the published credential registry and to the next even quiescent value *after* — so warm hits never return bytes that a concurrent retained-file check would deny (hits require a matching even epoch; once the writer acquires `PUBLISHED.write()` and disables the lock-free shortcuts, misses whose authorization consults foreign live generations wait on the writer — in the brief window between the odd epoch increment and shortcut disablement, warm hits already miss while a miss's check can still complete against the pre-update registry or single-generation shortcut, which is consistent with the registry at that instant, and a serving-generation match denies immediately) and fills sampled during an in-progress publication are never admitted; on Linux retained/fused fills (including worker `WouldBlock` and cold-compression pool hand-offs), 0.1.4's stricter retained-credential predicate denies (`404`) any known credential identity published by any live configuration generation at any link count (`0`, `1`, or `>1`) and fails closed on unreadable identity; on pooled/non-Linux fills, `identity_is_secret` governs the live response while an extra admission-only check refuses admission for any known live published credential at any link count; and whenever a serving generation carries `UNIDENTIFIED_CREDENTIAL` both cache hits and admissions are disabled (falling back to the 0.1.3 fresh path), while a foreign live generation's `UNIDENTIFIED_CREDENTIAL` marker leaves a clean serving generation's live response and Linux descriptor retention untouched while refusing cache admission. The full fallback resolver (the slow path for paths through symbolic links) is `v0.1.4`'s, and so is its known issue: the dotfile and forbidden-extension rules are checked on names, the file is opened afterwards, and a link switched in between by someone who can write to that document root can make a hidden file or a script's source from the same root answer (root confinement holds); the file cache does not extend it: **a response is admitted only when its file was opened by one kernel lookup of its whole path beneath the root that follows no symbolic link** (`openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`), because that lookup opens the names that passed the dotfile and forbidden-extension rules themselves, stays beneath the root and follows no link. What it does not promise, as no POSIX path lookup does, because its components are resolved one after another: **during a concurrent rename within the document root, the lookup can select a file that never had the requested pathname, including a file created only under a dotfile-denied ancestor. With `file-cache` enabled, later requests for the public URL can receive that file until the entry expires. Those requests need no filesystem permissions and need not overlap the rename.** (Without the cache only the request that overlapped the rename can receive it, as in `v0.1.4`.) Common real-world operations that rename directories inside a document root include **WordPress plugin and theme updates** (WordPress 6.3 and later move the old folder to `wp-content/upgrade-temp-backup/` and move the new folder into place) and **security clean-ups that move a plugin or theme folder away**. Root confinement and the refusal of links hold. No lookup available to the server closes this on a tree that can change underneath it; a site whose served tree is replaced as a whole and never renamed in place (an immutable release directory or snapshot) is not exposed to it. Never admitted, and answered for their own request exactly as in `v0.1.4`: (a) every response whose file the full resolver selected — any path that goes through a symbolic link or that the link-free lookup could not decide; (b) every response on a system where `openat2` is refused — a kernel older than 5.6, or a system-call filter, **including systemd's `RestrictSUIDSGID=yes`, which the packaged unit sets** — because the lookup then walks the path one `openat` at a time and opens the file through a directory descriptor it kept, and a directory moved in between could make it select a file that was never at the requested path; (c) every response on macOS, Windows and other platforms, where no such lookup exists. A later request is therefore never answered from such a selection. Consequence for operators: `file-cache` is accepted everywhere but **stores nothing unless the unit allows `openat2` (`--allow-openat2`) — i.e., it stores nothing under `RestrictSUIDSGID=yes`** — and stores entries only on Linux and Android when `openat2` is permitted and only for paths without symbolic links (when `openat2` is refused while `file-cache` is active, `miraserve check` and startup emit a one-time notice with that command). The fix that binds those rules to the opened file is developed separately and is not part of this change. Also never cached: any request carrying `Range` or `If-Range` (regardless of method or downstream header normalization, retaining whole-file `HEAD` semantics), directory redirects (`301`), `404` and other error responses, Markdown negotiation/conversion (`Accept: text/markdown` and authored `.md` sibling probes), bodies or base files above `256 KiB`, responses from any other handler (`fastcgi-pass`, `reverse-proxy`, `wasm`, `ai-publish`), quarantined sites, or `try-files` templates referencing `{query}` in the path segment.
    - **Memory, reload, and telemetry (0.1.5):** admitted payloads are copied into an exact-capacity buffer (`capacity == len`) only after reserving real sizes for body, body owner box, key, entry (including any stored `try-files` fallback candidate path), header storage, and shard hash tables from `file-cache-bytes`. Table accounting is conservative: replacing an existing expired/stale key updates the slot in place (`get_mut`) and never grows the table; during new-key growth the full new table is reserved before inserting while the old table stays reserved and is released only after inserting, nothing is refunded on the basis of `HashMap::capacity()` after deletions (only freeing an emptied shard refunds its table), and if reservation for the entry or its table share fails the entry is not inserted. Under pressure, one request examines at most 32 entries in total across any reservation retry (at most one shard) and the destination shard before serving uncached, leaving broader cleanup to the periodic sweeper; lowering `file-cache-bytes` takes effect atomically across concurrent reservations and `0` disables admissions at once. Body bytes remain charged while any slow reader still holds a response body after eviction or reload; minor residual overheads remain approximate (allocator rounding/fragmentation, cloned small header values held by in-flight `HEAD`/`304` responses, transient per-miss fill key strings during disk I/O, fixed shard arrays, and an old router held briefly by requests awaiting dispatch). Separately, the pre-existing on-the-fly compressed-response cache (`miraserve-static::compress`) is independent of `file-cache-bytes`: it is a process-wide LRU cache bounded to `64 MiB` of logical compressed body bytes (`COMPRESSED_CACHE_BUDGET_BYTES`), skipping single entries larger than `8 MiB` (`COMPRESSED_CACHE_MAX_ENTRY_BYTES`) and evicting oldest entries down to `56 MiB` when full (retaining encoder buffer capacity on stored `Bytes`). With `file-cache`, an on-the-fly compressed answer admitted on a fill is compressed from the file as read for that fill (never read from the compression cache), while requests not eligible for admission and sites without `file-cache` use the unchanged compression cache of earlier releases (keyed by device, inode, length, and timestamps). Every reload starts an empty file-cache generation and drops old entries (so policy changes such as `precompressed` never serve entries filled under the previous policy); expired entries are reclaimed lazily on lookup (releasing emptied shard maps) and by periodic 500 ms background sweeps: in normal server operation the cache generation is constructed on the **shared** Tokio runtime and captures that runtime's handle so sweeps always run on the shared runtime rather than on a worker loop (an embedder constructing `FileCache` outside a Tokio runtime without a captured shared handle falls back to `Handle::try_current()` on first admission when `!is_worker_loop_thread()`, which could select a worker runtime if first admitted from a worker runtime's blocking-pool thread). Each tick visits at most 16 shards and stops once a **soft threshold** of 256 examined entries is reached after finishing the current shard (up to **511** examined entries per tick when a 256-entry shard pushes a running total of 255 to 511); per-thread striped counters (`hit`, `miss`, `fill`, `not_cached_budget`) are summed on scrape via `miraserve_file_cache_events_total` (Prometheus) and `miraserve.file_cache.events` (OTLP).
  - Deployments behind Nginx, HAProxy, Cloudflare, or a load balancer **must** list the front proxy IPs/CIDRs in `server.limits.trusted-proxies` (prefer exact `/32` or `/128` proxy IPs; `/0`, `< /8` IPv4, `< /16` IPv6, `0.0.0.0/8`, `::/16`, non-zero host bits, and cumulative unions covering `>= 50%` of IPv4 or IPv6 space are rejected with `E007`; CIDRs broader than `/24` IPv4 or `/64` IPv6 emit warning `W022`). Trusted proxies are exempt from `max-connections-per-ip`, have their `X-Forwarded-For` chains peeled byte-wise right-to-left (joining multi-line headers, overwriting `X-Real-IP`, stripping client `Forwarded`, and propagating the effective client IP to rate limiting, access logs, FastCGI `REMOTE_ADDR`, and MCP gateway audit logs). Untrusted peers have spoofable forwarding headers (`X-Forwarded-*`, `X-Real-IP`, `Forwarded`) stripped on both reverse-proxy and FastCGI routes (`R7-XFF-3`). `miraserve check` emits warning `W021` when listening on a private/loopback or non-standard wildcard backend port without `trusted-proxies` at low `max-connections-per-ip` (wildcards on `:443` behind an L4/L7 load balancer must still configure `trusted-proxies` explicitly).
  - Header-keyed rate limits (`key="header:..."`) bound memory via `max-keys-per-ip` (default `64`, maximum `1024`) with atomic LRU eviction and fair-share congestion control so one noisy key cannot starve other users behind a shared NAT or CDN IP. Client-IP rate limits (`key="client-ip"`) automatically aggregate IPv6 buckets from `/64` to `/48` above 50% shard capacity and fall back to oldest-entry eviction on overflow so one IPv6 `/48` flood cannot lock out unrelated clients (`R7-RL-1`).
  - **Reverse-proxy request headers:** the upstream receives `Host` set to its own authority by default; `reverse-proxy { preserve-host #true }` forwards the client's `Host` instead (for backends that select a virtual host or tenant by hostname, as Nginx `proxy_set_header Host $host`, Apache `ProxyPreserveHost On` and Caddy's default do). For ordinary (untrusted) peers `X-Forwarded-For` and `X-Real-IP` are both set to the client address, `X-Forwarded-Proto` to the client scheme and `X-Forwarded-Host` to the client's host; `Forwarded` and `X-Forwarded-Port` are removed and never sent. With `preserve-host` the request is sent to the upstream over HTTP/1.1 (over HTTP/2 the `:authority` pseudo-header must stay the upstream's own name for connection and TLS routing). `reverse-proxy { allow-upgrades #false }` (default `#true`) stops WebSocket upgrades from being tunnelled: an upgrade request is forwarded as an ordinary request without `Upgrade`/`Connection: upgrade`. The importers accept a source header rule only when it produces exactly one of these results, and they emit `allow-upgrades #false` wherever the source did not tunnel WebSockets. On a `preserve-host` route a `health-check` must carry `host="<hostname>"`: probes are then sent over HTTP/1.1 with that host, so they reach the same virtual host as real requests (`E305` if it is missing, or if `host` is given without `preserve-host`).
  - **Outbound slow-reader & URI traversal protection (`R7-DOS-1`, `R6-HTTP-2`, `R7-HTTP-2`):** `server.timeouts` enforces `response-write-idle` (default `30s`) and `min-response-rate-bytes-per-sec` (also accepted under its older name `min-response-rate-bps`; the value is in **bytes** per second; default `1024`, `0` disables rate enforcement while keeping `response-write-idle` active) strictly during active socket/QUIC write backpressure across HTTP/1.1, HTTP/2, and HTTP/3 (never firing on idle keep-alive or quiet SSE streams). On Linux every accepted TCP connection sets `TCP_NOTSENT_LOWAT` to 32 KiB, so a client that stops reading is closed after `response-write-idle + 32 KiB / min-response-rate-bps` (62 s at the defaults) regardless of how large the kernel has grown the send buffer; on other systems the allowance is the send buffer itself, up to 1 MiB. The minimum-rate rule additionally forgives `response-write-idle` worth of data at the minimum rate: a receiver reopens its window in steps, so a steady reader is silent between lumps, and any silence shorter than `response-write-idle` is allowed. A client below the minimum rate still falls behind without limit and is closed. A client ahead of the minimum rate may spend its lead as silence (it holds that data in its own buffers and along the path): the silence limit grows by `lead / min-response-rate`, with the lead capped at 1 MiB, so a client that downloads fast and then stops reading holds its connection for at most `response-write-idle + (32 KiB + 1 MiB) / min-response-rate` (about 9 minutes at 2048 bytes per second, 18 at the default 1024). On HTTP/2 a response stream that makes no progress for `response-write-idle` while the socket is writable (the client closed the stream's flow-control window) has its body released and its connection shut down gracefully, and an HTTP/2 connection with no request in flight is closed after `idle-keepalive`. HTTP/2 keep-alive PINGs are not sent: a PING waits behind the response data already on its way, so a slow but acceptable reader could not answer it in time. On HTTP/1.1 `idle-keepalive` bounds the wait for the first byte of the next request and `header-read` runs from that first byte, each on its own clock. Anti-smuggling and reverse-proxy path validation strip RFC 3986 / Tomcat / Jetty `;params` before dot-segment traversal checks (`..;`, `.;`), reject double-encoded traversal (`%252e%252e`, `%255c`, `%2500`) on proxy routes, and reject RFC 3629 forbidden UTF-8 lead bytes `0xC0`, `0xC1`, and `0xF5..=0xFF` (including Latin-1 bytes in those ranges such as `%FC`) with `400 Bad Request` on all routes.
  - HTTP/2 flow-control windows default to `256 KiB` per stream and `4 MiB` per connection; size `max-connections` proportionally to host RAM on memory-constrained VMs.
  - **HTTP/2 small-DATA batching (`vendor/h2`):** MiraServe builds against `h2 0.4.21` with a minimal encoder patch (`COPY_LIMIT = 4096`; see `vendor/README.md`) so each selected `DATA` piece (already bounded by `max_frame_size` and stream/connection flow-control credit) strictly smaller than 4,096 bytes uses `h2`'s existing copy path into its encoder write buffer (16 KiB initial capacity) rather than chaining at upstream's 256-byte vectored threshold (1,024-byte scalar threshold). The same encoder rule applies both to downstream HTTP/2 response `DATA` and to upstream HTTP/2 reverse-proxy request `DATA`. On the wire, several already-ready small responses or requests (and control frames) may share a TLS record and a socket write; frame boundaries, per-stream ordering, `END_STREAM` / trailer framing, flow-control accounting, and genuine flush barriers remain entirely `h2`'s, with no batching timer and no added wait for a lone response.
  - **HTTP/2 in-task stream execution (0.1.5 — conditional behaviour change vs. 0.1.4):** In v0.1.4, `hyper` ran every HTTP/2 stream future on `TokioExecutor` as its own spawned Tokio task. MiraServe now selects the HTTP/2 stream executor **per connection** (`H2Exec` + `ConnDriver` in `crates/miraserve-http/src/h2_intask.rs`) and, on connections using `InTaskExec`, decides **per request** whether each stream runs inside the connection's task or as its own spawned Tokio task:
    - **Per-request execution rule:** In-task execution is used for requests classified as completing locally without waiting on another task; requests classified as waiting on another task, upgrades, and overlong request targets run on a spawned task. On an in-task connection, the service closure synchronously classifies each HTTP/2 request from the compiled router (`CompiledRouter::classify_h2_stream_exec`, zero filesystem I/O, zero heap allocation on canonical lowercase requests, exhaustive over `CompiledHandler`), except that `CONNECT` is handled by the service closure directly with the same spawned result, and passes the decision through a per-connection `AtomicU8` hand-off cell (`StreamHandoff`, never a thread-local) to `InTaskExec::execute`. **Hyper upgrade dependency:** this hand-off relies on `hyper 1.12.0`'s exact synchronous order inside `Serving::poll_server` (`proto/h2/server.rs:308–316`) — `service.call(req)` (`L309`), then per-stream `exec.clone()` into `H2Stream` (`L313`, which sees a pending decision and becomes `InTaskExecKind::UpgradeOnly` so `H2Stream::poll2`'s `execute_upgrade` at `L509` spawns directly without touching the cell), then `exec.execute_h2stream(fut)` on the original executor (`L316`), with no `.await` or fallible return in between — and on `hyper-util 0.1.21`'s `auto::Builder` passing the executor only to HTTP/2; it **must be re-reviewed on any `hyper` or `hyper-util` upgrade** (any hand-off mismatch counts in `HANDOFF_MISMATCHES`, falls back to spawning, and trips `debug_assert`, and `h2_intask::tests::per_request_handoff_detects_missing_decision_and_double_service_call` acts as a live-`hyper` test-time tripwire that fails on any change to that call/clone/execute order). **Spawned streams** bypass `Driven`, `IsolatedStream`, `PollBudget`, and `NONBLOCKING_INLINE_CONTEXT`, with Tokio owning their task lifetime, panic unwind, and drop: on the **shared runtime**, they match v0.1.4's `TokioExecutor` behaviour (`inline_work_must_not_block()` is `false`, so shared-inline static mode, synchronous logging, v0.1.4 proxy compression, and no inner WASM double-spawn); on **dedicated worker loops (`server { workers ... }`)**, they still spawn onto that worker's single-thread Tokio runtime where the worker-thread guard (`ON_WORKER_LOOP`, `inline_work_must_not_block() == true`) remains active, so the worker-thread non-blocking restrictions still apply to static I/O (`InlineMode::WorkerNonBlocking`), proxy compression (pool offload and yielding streaming), `acme-webroot` offload, and off-thread runtime diagnostics. Requests classified **spawned** are `reverse-proxy`, `fastcgi-pass`, `wasm-plugin`, `mcp-gateway`, `ai-publish.mcp-endpoint`, upgrades (`CONNECT`, extended `CONNECT`, `Upgrade`), authenticated `basic-auth` requests, overlong request targets (`> 8 KiB`, measuring the full target — scheme, authority, path, and query — identically to framing), `try-files` chains whose fallback targets a waiting handler (or a script directory index) on extensionless or non-`GET`/`HEAD` requests, and static/default roots with a routed script index on extensionless paths. Requests classified **in-task** are static files and directory listings, static/status `try-files` (and extensioned `GET`/`HEAD` assets under WordPress-style front-controller `try-files`), `redirect`, `respond`, immediate error responses decided without I/O, and ACME HTTP-01 requests that the responder will genuinely answer without I/O (non-`GET`/`HEAD` `405` or a token currently present in the lock-free in-memory `AcmeChallengeStore`, checked via borrowed `has_http01_token` without cloning or allocating on canonical lowercase hosts; missing or malformed tokens and `acme-webroot` disk lookups classify by site/auth/route like any other request). Requests classified in-task that later reach a waiting handler (e.g. via a site `rewrite` rule or a dotted front-controller slug) remain safe via the non-blocking context and offloads below.
    - **When in-task is used vs. `TokioExecutor` (conditional `openat2` probe):** Startup warms `/proc/sys/kernel/osrelease` BEFORE installing Landlock (`warm_nowait_kernel_probe()` and `warm_kernel_release()`) and selects the HTTP/2 execution mode using a strict pre-syscall filter so configurations that never call `openat2(2)` never probe it (keeping HTTP/1.1-only and proxy-only processes safe under outer seccomp policies that kill on `openat2`):
      1. **No HTTP/2 listener configured** (or redirect-only listener): no `openat2` probe -> `spawned`.
      2. **No static file work configured** (only `reverse-proxy`, `mcp-gateway`, `wasm-plugin`, `respond`, `redirect`, rootless `fastcgi-pass`, `acme-webroot` — which uses `openat` off the event loop — compile-time `error-pages`, and `basic-auth`; static file work consists of `site.root`, `ai-publish`, `static`, `try-files`, and `fastcgi-pass` with `route.root`): no `openat2` probe -> `spawned` (plain `TokioExecutor`, exact v0.1.4, because nothing in the configuration needs in-task execution). If a later hot reload adds static file work, reload re-evaluates and probes `openat2` + `RESOLVE_CACHED`: running connections keep their existing executor while new connections take the updated mode.
      3. **Non-Linux, or Linux outside 5.12–6.11** (or unreadable/unparseable `/proc/sys/kernel/osrelease`): no `openat2` probe -> `spawned` (both `RESOLVE_CACHED` [5.12+] and I/O-free buffered `preadv2(RWF_NOWAIT)` [5.9–6.11] are required for non-blocking inline static serving).
      4. **HTTP/2 + static file work configured + Linux 5.12–6.11:** startup probes `openat2(2)` and `openat2(RESOLVE_CACHED)` (the process already calls `openat2` on its first static request as in v0.1.4) and selects `in-task` iff both succeed, otherwise `spawned` (for example under systemd's `RestrictSUIDSGID=yes`). The lazy per-connection path applies the exact same four rules. Startup logs one `info` line stating whether HTTP/2 streams run `in-task` (static/local in-task, waiting handlers spawned) or `spawned` and why (and hot reload logs if the mode changes). `miraserve check` and startup include static HTTP/2 in the `openat2` refusal advisory ONLY on Linux **5.12–6.11** (never on Linux 5.9–5.11, where allowing `openat2` cannot enable `RESOLVE_CACHED`) and ONLY when HTTP/2 + effective static file work are active — startup uses the compiled router's effective serving inventory (`has_static_work()`, excluding quarantined tenant sites) and `miraserve check --fs` uses the classified config (excluding quarantined tenant sites) while leaving independent `workers` and `file-cache` advisory conditions unchanged — using the pre-sandbox cached kernel release rather than re-reading `/proc` after Landlock. HTTP/1.1 connections and HTTP/1.1 WebSocket upgrades do not enter the in-task stream driver or non-blocking inline context and keep v0.1.4 shared-inline behaviour on the shared runtime.
    - **What runs inline, on a spawned task, or on the blocking pool when in-task is active:** While `Driven` polls or drops an HTTP/2 stream future (which executes the request handler future, `hyper`'s `PipeToSendStream` response-body polls inside `H2Stream::poll2`, and synchronous stream drops), a closure-scoped `!Send`/`!Sync` thread-local guard (`with_nonblocking_inline_context`, setting `inline_work_must_not_block()` and restored on normal return and panic unwind; distinct from `is_worker_loop_thread()` so worker-loop-only rules such as file-cache sweeper placement keep their real meaning) routes blocking work off the connection task:
      1. **Static files (`RootReadPolicy` + mount-ID match + unsuitable-root spawned static task):** Each `StaticServer` computes `RootReadPolicy { mount_id, atime_free, nowait_refused }` once off the serving path when opened (startup, reload, `ai-publish` activation; never on a request) via `fstatvfs` (`ST_RDONLY | ST_NOATIME`) and `statx(AT_EMPTY_PATH | AT_STATX_DONT_SYNC, STATX_MNT_ID)` (Linux 5.8+; skipped — marking the root unsuitable with v0.1.4's exact root-open syscalls — whenever the warmed kernel release is outside Linux 5.9–6.11, when `openat2`/`RESOLVE_CACHED` is already latched unavailable, or in `CompiledRouter` when neither dedicated `workers` nor Linux 5.12–6.11 HTTP/2 is configured; below 5.8 or on failure/missing `STATX_MNT_ID`, unknown counts as unsuitable; refreshed on every reload — a live remount without a reload keeps the prior answer). On a **suitable** (`atime_free`, not refused) root, static lookups and small-file reads (`<= 256 KiB`) use `openat2(RESOLVE_CACHED)`, `statx(AT_EMPTY_PATH | AT_STATX_DONT_SYNC, STATX_BASIC_STATS | STATX_MNT_ID)`, and `preadv2(RWF_NOWAIT)` ONLY when the file's `mount_id` equals the root's `mount_id`: pre-selection `Unknown`/`EAGAIN` misses, undecidable precompressed siblings, and deferred paths (`RetentionPolicy::DEFERRED`: authored `.md`, HTML-to-Markdown conversion, and serving generations carrying `UNIDENTIFIED_CREDENTIAL`) resolve afresh on the blocking pool (preserving single-pass script-vs-static decisions across sibling `Unknown` recovery), while post-selection `RWF_NOWAIT` `EAGAIN`/short reads, nested-mount `mount_id` mismatches, non-blocking `statx` authorization misses, and cold on-the-fly compression hand off to the blocking pool with the selected descriptor retained; the first `preadv2(RWF_NOWAIT)` refusal (`EOPNOTSUPP`/`EINVAL`/`ENOSYS`/`EPERM`, e.g. `overlayfs`/`tmpfs`) permanently latches `nowait_refused` on that root so later requests skip the zeroed buffer and syscall completely and treat the root as unsuitable. On an **unsuitable** root (default writable `relatime` mounts, Linux < 5.8, unknown `mount_id`, or latched `nowait_refused`) during an in-task HTTP/2 `GET` on the shared runtime, that request's static serving runs as its own spawned Tokio task in `InlineMode::SharedInline` (v0.1.4's per-stream model without a blocking-pool hop; the scoped `NONBLOCKING_INLINE_CONTEXT` is not inherited, and `AbortOnDrop` + panic propagation preserve cancellation, in-flight accounting, access records, and write tracking), while `HEAD`, non-read methods, `try-files` `=status`, and warm `file-cache` hits stay in-task; large files (`> 256 KiB`) always stream via batched positional blocking-pool reads.
      2. **Reverse-proxy compression:** reads the complete `Accept-Encoding` field value across all request field lines combined in order (RFC 9110 §5.2) and evaluates it through **one** RFC 9110 §12.5.3 / §12.4.2 negotiation function (`negotiate_proxy_accept_encoding`: explicit weights, `x-gzip` normalized into `gzip` per RFC 9110 §8.4.1.3 — the sole registered alias for any coding MiraServe produces per RFC 9110 §18.6, emitted as canonical `Content-Encoding: gzip`, with positive weights taking `max` and any `q=0` on either spelling failing closed — `*` applying to unlisted codings and `identity` per RFC 9110, `q=0` exclusions failing closed, malformed or out-of-range weights outside `0..=1` or with >3 fractional digits rejecting that member, ordered by descending weight with ties broken by server preference **`zstd > br > gzip`**) and one decision function (`ProxyEncodingDecision`) implementing the invariant across all three paths: **(a)** when `identity` is acceptable, selection matches v0.1.4 (`accepted_encodings`, so a bare `*` or bare `x-gzip` still gets identity and ordinary clients are unchanged; at saturation, compression is shed and the response goes out uncompressed with `Vary: Accept-Encoding`); **(b)** when `identity` is NOT acceptable, selection picks the first acceptable coding from the RFC-ordered list restricted to what the path can produce — buffered unsaturated `{zstd, br, gzip}`, streamed and saturated `{br, gzip}` (so whenever `identity` is excluded and a coding that path can produce is acceptable — including wildcard-only `zstd` such as `br;q=0, gzip;q=0, *;q=1, identity;q=0` on the buffered path and `x-gzip, identity;q=0` -> `gzip` on buffered, streamed, and saturated paths — the proxy never sends identity, while still honoring all normal response eligibility guards: `HEAD`, `1xx`, `204`, `304`, `206`, empty body, existing `Content-Encoding`, `Content-Range`, digests, `no-transform`, `x-accel-buffering: no`, compressible MIME, and size/trailer limits). Response-level guards are split into two groups with one `Vary: Accept-Encoding` append site between them (no per-arm appends): **categorical guards** (`1xx`, `204`, `206`, existing `Content-Encoding` or `Content-Range`, visible digest header or advertised digest trailer, `Cache-Control: no-transform`, and non-compressible or missing media type including SSE — responses MiraServe never transforms regardless of body or framing) return immediately with upstream headers untouched (no `Vary` added, matching v0.1.4). For the two cache-updating bodiless response kinds, `304 Not Modified` (RFC 9111 §4.3.4, whether or not it carries `Content-Type`) and `HEAD` (RFC 9111 §4.3.5, whenever it passes the non-method categorical guards, with missing `Content-Type` treated as transformable): when the upstream response already carries a `Vary` header field, it passes through that single `Vary: Accept-Encoding` append site (merging `Accept-Encoding` across all upstream `Vary` field lines, leaving `Vary: *` untouched and avoiding duplicates) and returns immediately without touching the body so a cache replacing the stored `Vary` on update (RFC 9111 §3.2) cannot drop `Accept-Encoding`; when the upstream response has no `Vary` header field, it is forwarded untouched (matching v0.1.4) so a cache leaves any stored `200` `Vary` dimensions (such as `Accept-Language, Accept-Encoding`) intact (RFC 9110 §9.3.2, RFC 9111 §3.2). Every response passing the categorical guards receives `Vary: Accept-Encoding` in that one place (merging with existing upstream `Vary` values and leaving `Vary: *` untouched) for every request whatever `Accept-Encoding` it carried or lacked, before **instance guards** (already-ended body, `UpstreamHasDigestTrailer` extension after trailer-header stripping, `X-Accel-Buffering: no`, declared `Content-Length` outside `1,024..=4 MiB`, and late buffering exits for bodies over the cap, under the minimum, with trailers, or with body errors) and before consulting `ProxyEncodingDecision` (so every instance-guarded exit and every negotiated outcome — compressed, expanded-therefore-identity, identity by choice, saturated, failed, and streamed — structurally carries `Vary: Accept-Encoding`, a strict superset of v0.1.4). When `inline_work_must_not_block()` is active (in-task HTTP/2 safety net and dedicated worker loops), buffered bodies `> 64 KiB` consume `frames` into a single contiguous buffer before awaiting (zero-copy for single-frame bodies, no duplicate copy across `.await`) and compress on the blocking pool under the 8-permit semaphore plus the **32 MiB** process-wide waiter byte budget (8 × 4 MiB active + 32 MiB waiting = **64 MiB** across waiting and active **input payloads only**, excluding body collection, encoder output buffers, allocator overhead, and downstream transport bodies); at saturation (all 8 permits busy and waiter budget full) when `identity` is excluded and `{br, gzip}` is acceptable, compression falls back to `YieldingStreamingCompressedBody` over the buffered bytes using no permit and no extra waiting buffer; unknown-length streamed bodies use `YieldingStreamingCompressedBody` (bounded to 64 KiB per poll). **Residual (RFC 9110 §12.5.3):** RFC 9110 §12.5.3 states a recommendation with an exception (*"the origin server SHOULD send a response without any content coding unless the identity coding is indicated as unacceptable"*); if and only if the intersection with the path's producible set is empty (streamed or saturated with only `zstd` acceptable, or no supported coding acceptable) or a buffered compressor fails, MiraServe preserves the upstream response and sends it uncompressed with `Vary: Accept-Encoding` as in v0.1.4 rather than replacing it with `406 Not Acceptable`. (The static path's `Accept-Encoding` parser in `miraserve-static` is unchanged.)
      3. **WASM plugin invocations:** run as their own spawned Tokio task and are awaited under an `AbortOnDrop` guard (preserving stream-drop cancellation, slot release, trap/timeout errors, and panic propagation via `resume_unwind`) so concurrent plugins on one connection do not serialize on a single core; Wasmtime's execution timeout starts at the spawned task's first poll (excluding scheduler queue delay, so wall-clock deadline satisfaction is not guaranteed under scheduler saturation).
      4. **Interrupted access-log and runtime diagnostic emission (shared bounded single-drainer queue):** Both interrupted access-log emission and runtime tracing diagnostics share one generic bounded off-thread queue (`OffloadLogQueue`, two independent instances), each drained FIFO by at most **one** `spawn_blocking` drainer task at a time (releasing ownership exactly once under the queue lock with the unwind guard disarmed on normal exit, and on sink-panic unwind restoring any remaining un-emitted batch items to the front of the queue and scheduling a replacement drainer so queued records are never stranded) and bounded to an **approximate 1 MiB** payload cap (counting formatted line / estimated record string bytes, excluding allocator overhead and the drainer's single local batch of up to 64 records) and **4,096 records** with drop-oldest eviction, monotonic drop counters (`offloaded_access_log_dropped()`, `offloaded_diagnostic_log_dropped()`), and stderr drop summaries rate-limited strictly to 30 s (including when the queue empties). For **access logs**, formatting stays inline (`ACCESS_LINE`) while emission inside `in_nonblocking_inline_context()` (`AccessLogBody::finish_now`, `AccessLogBody::drop`, `ConnWriteTracker::enqueue_or_emit_failed`, `IsolatedStream::drop`) enqueues onto the access-log instance; offloaded interrupted records remain FIFO relative to each other but may interleave with or trail synchronous successful-flush records (`WriteOutcomeIo::poll_flush` -> `mark_flushed` stays on the connection task as in v0.1.4). For **runtime diagnostics** (`--log-file`, `stderr`, `stdout`), the runtime tracing writer checks `inline_work_must_not_block()`: when `true` — during in-task HTTP/2 stream polls, drops, and `log_stream_panic`, and on dedicated worker loops while the worker guard is live (including listener-registration errors and worker teardown inside that guard) — each formatted event line (carrying its emission timestamp, covering proxy upstream failures, FastCGI stderr warnings, MCP audit logs, and router/auth/WAF warnings) is enqueued onto the diagnostic instance, so a tracing event emitted before unwinding leaves a guarded poll is queued and can be lost on an immediate abort; when `false` — default spawned mode, HTTP/1.1, shared-runtime startup/shutdown, dedicated-worker runtime construction and pre-guard Landlock checks, and blocking-pool threads (which never inherit the guard, so their Landlock error immediately before `abort()` stays synchronous) — it writes synchronously as in v0.1.4, and Rust's own panic hook always writes directly to `stderr`. Diagnostics emitted inside the guarded context may trail or interleave with synchronous lines (each carries its timestamp) and can be dropped under overload (`offloaded_diagnostic_log_dropped()`). Graceful shutdown drains both queues under **one** 2-second deadline measured from the caller (records held in a drainer's local batch count as outstanding, and records enqueued while a Tokio runtime is shutting down hand off to a detached drainer thread rather than stranding); an incomplete drain logs a warning with remaining counts only and does not alter the process exit status (which remains decided by the rotating access writer's final flush alone, exactly as in v0.1.4, so `SIGTERM` under load does not trigger `Restart=on-failure`). The drain report distinguishes `connections_forced_closed` (graceful connection-drain deadline expired with connections still open, force-closed without joining as in v0.1.4) from `workers_join_timed_out` (one or more dedicated worker threads did not join within the shutdown grace period); either marks the report not clean and emits a warning reflecting which condition prevented certifying a clean shutdown.
      5. **`acme-webroot` and existing pool work:** `acme-webroot` challenge token lookups and 4 KiB reads (using `openat`, never `openat2`) offload to the blocking pool; static on-the-fly compression, HTML-to-Markdown conversion, `bcrypt` checks, and MCP publish already run on the blocking pool. Bounded CPU work (RFC 9421 / MCP Ed25519 signature verification, access-log formatting) stays inline.
    - **Panic isolation, bounds, and allocations:** Every in-task stream poll and drop is wrapped in `std::panic::catch_unwind`, dropping only that stream's `hyper` future and RAII guards (`InFlightRequestGuard`, `H2StallBody`, `AccessLogBody`) while sibling streams and the connection continue unaffected; **when the stream is still open**, dropping the `h2` handle schedules `RST_STREAM(CANCEL)` (an already-closed stream emits no reset, and `h2` emits `RST_STREAM(NO_ERROR)` if the response send side already closed cleanly while the request receive side remained open). `MAX_STREAM_POLLS_PER_POLL = 64` and `MAX_OUTER_ITERATIONS = 4` (plus Tokio's cooperative task budget) bound **stream polls and outer accept/poll iterations per `Driven::poll` turn** — they do not bound elapsed wall-clock time of an individual poll, the number of stream accepts inside one `hyper` connection poll, or the cost of moving a queued batch into `FuturesUnordered`. `Driven::streams.len()` is not strictly bounded by `max_concurrent_streams` (default 128) because a client `RST_STREAM` can release a protocol slot before `Driven` polls and drops that future; in practice it is bounded by `max_concurrent_streams` plus pending-drop reset futures (rate-limited by `max_pending_accept_reset_streams` and `max_h2_rst_stream_per_sec`, default 50/s; HTTP/2 `CONNECT` streams and their `UpgradedSendStreamTask` futures spawn directly onto Tokio via `InTaskExec::UpgradeOnly` and never enter `Driven::streams`). Each admitted future uses two allocations (`Box::pin` for the future and `FuturesUnordered`'s `Arc<Task>` node); `Driven` polls the stream inside the connection task.
    - **Limits and P2 residuals that remain when in-task is active:** (1) On supported `noatime`/read-only local roots, remaining P2 residuals are `fanotify` permission listeners, filesystem-specific waits (such as an ext4 DAX extent lookup), and a live mount remount between reloads (refresh happens on reload); (2) the successful-flush access-log path (`WriteOutcomeIo::poll_flush`) remains on the connection task as in v0.1.4; (3) all non-offloaded handler and framing work across the streams of a **single** HTTP/2 connection shares one task and one CPU core at a time (interleaving at `.await` points), while distinct connections, blocking-pool jobs, spawned static tasks on unsuitable roots, and spawned WASM plugin tasks run across all cores. No configuration key or stream-count spawn threshold is added (see `docs/PERF_PLAN.md` §8.4).
- **Per-site plain HTTP on `redirect-https=#true` listeners (0.1.3):** Each `site` defaults to `http "redirect"`, preserving the exact v0.1.2 port-80 behaviour (ACME HTTP-01 tokens, `400` on missing/invalid `Host`, `421` on unknown hosts, `308 Permanent Redirect` to HTTPS for configured hosts). When no site sets `http "serve"`, every request on the redirect listener goes straight to the unmodified v0.1.2 redirect responder with no extra site lookup. Setting `http "serve"` on a `site` dispatches matched **HTTP/1.0 and HTTP/1.1** requests through the normal request pipeline with the connection marked plain HTTP (`is_https = false`). Cleartext HTTP/2 (`h2c`) on that listener is never served: any HTTP/2 request receives the exact v0.1.2 redirect-listener answers (ACME token, `400`, `421`, `308`) regardless of the site's `http` mode. When at least one site uses `http "serve"`, every HTTP/1.x request with an unambiguous `Host` matching a serve-mode site goes straight to the normal pipeline — which runs framing (`414` on overlength paths before path decoding, `413`, `431`, `400`), path canonicalization, and ACME HTTP-01 lookup once, identically to HTTPS — so all serve-mode rejections and blocks are logged and counted identically to HTTPS with framing strikes counted once; HTTP/2, bad/missing/ambiguous `Host`, unknown hosts, and `http "redirect"` sites take the unmodified v0.1.2 redirect responder. IPv6 `Host` values (`[::1]`, `[::1]:80`) are served for configured `http "serve"` sites while `http "redirect"` keeps v0.1.2 validation unchanged. On plain-HTTP responses, `Strict-Transport-Security` and `Alt-Svc` are never emitted (and are stripped if set by an upstream, script, plugin, or header rule), while all other configured security headers apply as on HTTPS. FastCGI omits `HTTPS` and sets `REQUEST_SCHEME=http` and `SERVER_PORT` to the plain-HTTP listener's port; reverse-proxy routes forward `X-Forwarded-Proto: http` and support WebSocket upgrades with identical graceful-drain accounting; on plain-HTTP connections, RFC 9421 bot-auth `@scheme` binds to the connection's scheme (`"http"`, including for absolute-form targets) while HTTPS preserves v0.1.2 selection; server-generated redirects (directory slash and relative `redirect`/`rewrite` targets) remain relative and preserve scheme and port; and access-log lines remain byte-identical to v0.1.2 on HTTPS (no `scheme` field), while plain-HTTP access-log lines append `scheme="http"`. By default (`credentials=#false`), any `basic-auth` area or OAuth/JWT `mcp-gateway` reached over plain HTTP is answered `403 Forbidden` (`Cache-Control: no-store`), checked before `Content-Encoding`, `Upgrade`, or any other request inspection, without issuing `WWW-Authenticate` (even if site or route `headers` rules add one) and without evaluating credentials or Bearer tokens. Setting `http "serve" credentials=#true` explicitly opts that site in so `basic-auth` and OAuth/JWT `mcp-gateway` routes behave over plain HTTP identically to HTTPS (`401` + `WWW-Authenticate` challenge, credential/token verification, shared failure-throttling tables and limits, and `Cache-Control: no-store` wherever the HTTPS answer carries it: basic-auth answers do, the gateway's own `401` does not on either transport, with plain-HTTP RFC 9728 `resource` URLs preserving any non-default port from `Host` while HTTPS preserves v0.1.2 URL construction); specifying `credentials` on `http "redirect"` is a configuration error (`E003`), and unknown properties are rejected as errors. `miraserve check` omits default `http` (`redirect`, `credentials=#false`) from `--dump-normalized` output so existing files remain byte-identical to v0.1.2, emits warning `W031` when a site sets `http "serve"` without any `redirect-https=#true` listener, warning `W032` (`passwords for <site> travel unencrypted over plain HTTP (http "serve" credentials=#true)`) for each site setting `http "serve" credentials=#true`, and prints an informational note listing the hostnames served over plain HTTP when a `redirect-https=#true` listener is present. Changing `http` or its `credentials` property takes effect on live reload for both new and open keep-alive connections. Behind a front proxy that terminates TLS and forwards plain HTTP (for example Cloudflare's "Flexible" mode), an application that itself forces HTTPS redirects for ever, because the proxy's request reaches it as plain HTTP; use end-to-end TLS ("Full (strict)") there rather than `http "serve"`.
- **Precompressed static siblings (`precompressed`, 0.1.4 — default change):** Each `site` block (and any route-level `static { ... }` block, which inherits the site policy when omitted and overrides it when specified; `try-files` routes inherit the site policy) accepts `precompressed`: `"off"` (no `.zst`/`.br`/`.gz` sibling is ever probed or served; on-the-fly compression is unchanged), one or more encoding names from `"zst"`, `"br"`, `"gz"` (probed only for the listed encodings, in negotiation order `zst > br > gz`), or `"all"` (v0.1.3 behaviour). Configuration error codes (verified via `miraserve check`): missing arguments, non-string arguments, or child blocks fail with `E004`; unknown properties fail with `E003`; duplicate values, duplicate directives in the same block, or duplicate properties fail with `E005`; unknown encoding names or mixing `"off"`/`"all"` with other values fail with `E203`. **Behaviour change vs. v0.1.3:** an omitted `precompressed` directive now defaults to `"off"` (v0.1.3, where compression is enabled for the site or route, probed the sibling extensions matching the request's `Accept-Encoding`, up to all three, on every request carrying one and no effective `Range`; on direct and plain static dispatch a `HEAD` request has its `Range` removed before static serving, so it probed as well, while a `try-files` route passed the header through and a `HEAD` with `Range` probed none). The policy filters only the sibling probe loop; base-file resolution first, dotfile/forbidden-extension/credential checks on siblings (with the sibling's own status read after closing the base file), `Vary`, validators, `Range`, `HEAD`, `304`, and immediate pickup of newly published siblings on the next request without caching negative lookups between requests are unchanged, and policy changes take effect on live reload. In `miraserve check --dump-normalized`, the built-in default (`precompressed "off"` on a `site`, and omitted/inherited `precompressed` on a route `static` block) is omitted so existing v0.1.3 configurations keep byte-identical normalized dumps, whereas any explicit route-level `static { precompressed ... }` override is always emitted (including `"precompressed": []` when explicitly set to `"off"`) so configurations with different effective policies never dump identically. `miraserve check` prints an informational note ("sites that configure `precompressed`: ...") listing once each site whose configuration turns the policy on, host aliases grouped (a summary of the configuration: a `static` route with `compression #false` is left out, and the note does not claim that a request will probe a sibling), strictly capped at 2,048 bytes total including prefix, any truncated over-long entry, and omission suffix.   - **Single open & descriptor retention:** Where a request has already opened a readable, confined regular leaf for the current request, root, route, canonical path, and representation (direct file, plain directory index, script-routed static directory index, or a `try-files` candidate), serving uses that retained descriptor rather than reopening the path. An undecidable post-selection inline check (such as an in-root symlink precompressed sibling or a transient metadata error producing `Unknown`) can discard that inline selection and recover on the blocking pool (on the combined script-routed and `try-files` paths, re-resolving only the selected static candidate's representation without repeating an already completed script-routing decision; on a plain static site, resolving the original request again as in v0.1.3). Static directory-index descriptor reuse is never carried across an internal rewrite, another root, or a public two-step `Lookup` — the public two-step API preserves v0.1.3's token shape and descriptor ownership (an inline direct-file token still carries its direct-file descriptor as in v0.1.3, a directory probe carries no static-index descriptor, and a pooled probe leaves `Option<Lookup>` as `None`). Its responses fall under the same concurrent-mutation exception as everything else here: with credentials configured, the decision-time status read refreshes the carried descriptor's metadata, so if the file is replaced between the two steps its validators can differ from the probe-time validators v0.1.3 used (the old name's unlink advances the inode change time), and an `If-None-Match` carrying the earlier tag can then get `200` where v0.1.3 answered `304`. Deferred Markdown paths (authored `.md` siblings or HTML conversion) and serving generations carrying `UNIDENTIFIED_CREDENTIAL` disable the new single-pass reuse, status-read fusion, and cold-compression descriptor transfer, taking v0.1.3's path (in the two-step API, a serving generation with `UNIDENTIFIED_CREDENTIAL` consumes an inherited direct-file `Lookup` token with v0.1.3's decision-time credential check, as in v0.1.3).
  - **Atomic replacement:** If a selected file (such as `index.html` after a qualifying script-index probe or a `try-files` candidate) is atomically replaced while the request is in flight and the request stays on the retained path, the in-flight `GET`, `HEAD`, `Range`, `If-Range`, or conditional request completes against the retained old descriptor, while the first request started after replacement completes resolves names fresh and serves the replacement.
  - **Withdrawal and type swaps:** If a selected public leaf is unlinked or replaced by a symlink, directory, or special file after selection, the in-flight request can still complete from its already-opened confined descriptor (a replacement symlink is never followed through that descriptor); subsequent requests observe the withdrawn or replaced path (`404`, redirect, or symlink checks). A directory probe alone authorizes no child: every unopened index or precompressed sibling resolves fresh through root confinement.
  - **Permission revocation (first-open permission semantics):** Because the confined readable open occurs once at selection, revoking leaf read permission, an ACL, or ancestor directory traversal permission after selection does not retroactively fail an in-flight request that stays on its retained descriptor (a leaf `fstat` cannot re-evaluate pathname traversal, ancestor permissions, or Landlock pathname rules). Subsequent requests observe the revoked permissions for that file and refuse to open it — failing closed (`404`) on a direct or plain static route unless an independently readable, enabled precompressed sibling answers the request (the full resolver can stat the base and open a readable precompressed sibling before attempting to open the base for reading); a request for a directory without its trailing slash can still be redirected (`301`) to the slash form when the directory's index can be stat-ed but not read, because the index is selected by its metadata before it is opened for reading, and the request for the slash form then fails closed unless such a sibling of the index answers it; or falling through to another `try-files` candidate or a winning script route when one applies.
  - **Parent rename or replacement:** If an ancestor directory is renamed, moved outside the public tree, or replaced by a regular file after the leaf was opened under confinement, the in-flight request can still complete from the originally confined leaf descriptor; subsequent requests resolve from the configured root capability.
  - **In-place writes (no snapshot promised):** An open descriptor pins the inode, not its bytes. Concurrent in-place writes, truncation, or repurposing of the inode can be seen by the in-flight read; length, validators (`ETag`/`Last-Modified`), range bounds, and compressed-cache keys are taken from the selected descriptor's metadata, and existing bounded reads remain enforced. A streamed file that ends before the advertised length ends the response body there, exactly as in v0.1.3 and on every platform: over HTTP/1.1 the connection is closed after the short body, over HTTP/2 and HTTP/3 the stream ends short of its `content-length` (a length-checking client reports the transfer as failed), and an HTML-to-Markdown conversion converts what was read and answers with the length of what it produced.
  - **Script/index publication & representation changes:** An already-selected static winner can finish; on the combined script-routed and `try-files` paths, if an undecidable precompressed sibling sends that static winner to the blocking pool, pool recovery re-resolves only the selected static candidate's representation and does not repeat script selection. On a plain static site (no script route), a pool retry resolves the original request again as in v0.1.3, so a higher-priority static index published before dequeue can win. A script winner still dispatches through the router with full target policy; a newly published precompressed sibling can still win if encoding negotiation has not yet run.
  - **Retained-credential rule, authorization ordering, and packaged walk:** Wherever a descriptor is reused or its single `fstat` doubles as authorization (direct file, plain directory index, script-routed static index, or direct `try-files` leaf with no intervening probes), authorization checks the descriptor's `(dev, ino)` identity against **all** known credential identities published by **any** live configuration generation regardless of link count (`nlink` `0`, `1`, or `>1`) immediately before releasing bytes, validators, `304`, range metadata, or cached compressed content — intentionally stricter on purpose than v0.1.3's fresh predicate, which consulted foreign live lists only above one link. The `UNIDENTIFIED_CREDENTIAL` fresh-resolution exception is scoped to the **serving** generation only: when the serving generation carries `UNIDENTIFIED_CREDENTIAL`, single-pass reuse, fusion, and cold-compression descriptor transfer are disabled and the request takes the v0.1.3 path (including consuming an inherited direct-file `Lookup` token with v0.1.3's decision-time credential check in the two-step API) without broadening denials for ordinary stable files. A marker in another live generation never causes a clean serving generation to abandon a selected descriptor, while every live generation's known identities remain enforced at any link count. Deferred Markdown paths (`serve_canonical_unfused` for authored `.md` siblings and HTML-to-Markdown conversion) likewise disable reuse, fusion, and cold-compression descriptor transfer so they reopen and resolve afresh at dequeue exactly as in v0.1.3. A failed inline classification or fused status read returns `Unknown` and recovers via the authoritative blocking pool (never an inline `404`); a definite credential match denies with `404` before validators, ranges, or bytes (and a secret precompressed sibling never falls through to a lower encoding); and an unreadable identity in the authoritative resolver fails closed. When there are credentials to protect (an active own or live published credential list), late decision-time status reads stay whenever selection required an earlier classification or intervening step (after precompressed sibling probes, after closing the base descriptor on a winning sibling, after blocking-pool dequeue including cold-compression handoff, or after a two-step script-index probe — including when a pooled probe's breaker pause expired before serving). On the packaged Linux `openat` component walk (used when `openat2` is unavailable or filtered, e.g. systemd `RestrictSUIDSGID=yes`), the owned immediate parent descriptor is closed before leaf status classification and authorization (`open leaf -> close parent -> status and authorize`), while the shared root capability is never closed.
  - **Inline circuit breaker timing (Linux combined operations only):** On Linux combined inline operations (including synchronous small-file reads and `Unknown` exits, excluding pool queue time, Markdown conversion, and async waits), the whole operation is timed as one monotonic interval against the unchanged `< 2 ms` (`-1`), `>= 2 ms` (`+8`), and `>= 24` (reset to `0`, `5 s` pause) thresholds, with independent eligibility decisions for each subsequent `try-files` candidate, internal rewrite target, or post-handoff operation. This changes accounting in both directions relative to v0.1.3: two slow phases within one combined operation earn one `+8` increment (and an admitted slow probe proceeds to a slow small-file read without a mid-operation pause check), whereas two sub-threshold phases summing to `>= 2 ms` (for example `1.2 ms + 1.2 ms = 2.4 ms`) now earn one `+8` where both phases previously cooled the score by `-1` each. The two-step directory probe (used on Android and on Linux non-combined paths) retains v0.1.3's separate directory-open and index-scan breaker intervals; macOS, Windows and the other platforms have no inline lookup, resolve on the blocking pool as in v0.1.3, and so have no inline interval to time.
  - **Large streamed static files (`> 256 KiB`, all platforms):** Files and byte ranges larger than `256 KiB` stream lazily on the **blocking pool on every platform** (never inline on serving threads) directly from the selected descriptor (`Arc<std::fs::File>`, no `tokio::fs::File`), tracking the next delivery offset and undelivered length. Reads are always positional (`pread` into `rustix::buffer::spare_capacity` -> `Bytes` on Unix/Android with zero pre-zeroing and zero extra copy; `FileExt::seek_read` -> `Bytes` on Windows with zero extra copy); `seek` is never called anywhere, so a large non-zero `Range` request needs no seek-related lookup hand-off on worker loops.
    - **Batched pool reads and frame discipline:** A blocking-pool task is submitted only when `poll_frame` is called with nothing queued and nothing in flight; it never waits for network credit, reads up to **four `64 KiB` chunks (`STREAM_BATCH_CHUNKS = 4`, up to `256 KiB`)** in separate `<= 64 KiB` allocations (keeping wire frame sizes unchanged), and returns them as separate frames. Queued frames are drained one per `poll_frame` before another pool task is submitted, so a slow reader never pins a blocking thread between batches. The delivery offset advances strictly by bytes actually emitted; `size_hint` and `is_end_stream` include queued bytes, and once a body poll has RECEIVED a batch result that ended in early EOF or a read error (a finished task that has not been polled yet still shows the advertised countdown) `size_hint` narrows to the queued bytes actually still to be delivered while a pending error keeps `is_end_stream` false until reported; successful frames are drained before a later error or early EOF is reported; no read crosses the selected range boundary; and a short or zero read inside a batch ends the batch there (a response whose batch observed early EOF ends there after the frames already read, as in `v0.1.3`/`v0.1.4`, even if the file regrows while earlier frames drain). Dropping the body aborts any queued pool task or lets an already-running batch finish and drop its descriptor and buffers without leaking.
    - **Process-wide speculative budget (`64 MiB`) and HTTP/2 lookahead:** Speculative bytes (chunks beyond the first of a batch — up to three extra chunks = `192 KiB`, capped to what the remaining length actually needs; a task whose remaining length fits in one chunk reserves `0`) are reserved without waiting from a process-wide **`64 MiB`** speculative budget before dispatch, counting in-flight tasks, completed results awaiting a poll, and queued frames, and released on delivery, EOF, error, or cancellation (with ownership following a running task that survives body drop). When the budget is exhausted, the body immediately falls back to reading **one chunk (`<= 64 KiB`)** per pool task (zero speculative bytes). Because hyper's HTTP/2 writer polls one frame before reserving send capacity, each initially zero-window HTTP/2 stream holds up to **`256 KiB`** of **body and hyper lookahead payload** (one demanded `<= 64 KiB` frame held by hyper / `PieceBody` plus up to three `64 KiB` speculative frames in the body): for `100` zero-window streams that is at most `25 MiB` of body and hyper lookahead payload (`18.75 MiB` speculative + `6.25 MiB` demanded), and for `10,000` zero-window streams at most `64 MiB` speculative process-wide (~341 full batches) plus one demanded `64 KiB` frame per stream — about `689 MiB` of body and hyper lookahead payload — with further streams degrading immediately to 1-chunk reads. These figures cover body and hyper lookahead payload only and exclude allocator overhead and data already in downstream transport buffers (for example earlier DATA buffered in `h2`, TLS, or kernel socket buffers on a stream that previously had credit).
    - **In-place visibility contract (refines the in-place writes rule above):** Because one batch fetches up to three chunks beyond the frame being delivered, bytes already fetched in a batch can outlive a concurrent in-place truncation or overwrite by **at most three chunks (`192 KiB`)**, measured from the **last body poll that RETURNED a DATA frame before the change, with no body poll in between** (not from bytes observed on the client socket, by which time later body polls may already have run; a poll that returned `Pending` may already have dispatched a task for four chunks, all `256 KiB` of which can be read before the change and delivered after it). One consequence for HTTP/1.1 access records: when a batch returns data and then an early EOF, the last frame it returned is the body's end, so a final flush that succeeds can be recorded as `completed=true` for a transfer shorter than the advertised length (the client still sees a short response and the connection is not reused; the record's byte count is the bytes actually sent); in `v0.1.4` that case reached hyper's incomplete-length error path. Concretely, after frame 1 (`64 KiB`) is returned by a body poll and before any subsequent body poll: an in-place truncation to `100 KiB` yields `100 KiB` to `256 KiB` of the original prefix (never more), and after a completed same-length in-place overwrite, every byte from offset `256 KiB` onward reflects the new content. A response whose batch observed early EOF ends at that observed EOF even if the file regrows while earlier frames from the batch drain.
    - Streamed files are never admitted to `FileCache`, and cold on-the-fly compression (`256 KiB < len <= 4 MiB`) continues to run on the blocking pool. Below TLS, `WriteGuardedIo` forwards `poll_write_vectored` and `is_write_vectored` with exact byte, stall-timer, and `min-response-rate-bps` accounting so `tokio-rustls` can flush multiple encrypted TLS records per socket write (`writev`).
- **Linux in-process seccomp-bpf set-ID filter and `service generate --allow-openat2` (0.1.5):**
  - **In-process set-ID policy (`miraserve-sandbox`):** Whenever MiraServe installs a seccomp-bpf filter (`server.sandbox.seccomp "strict"` or `"standard"`, always on Linux regardless of whether the systemd unit sets `RestrictSUIDSGID=yes`), the filter enforces two sets of rules returning `EPERM`:
    1. **Scalar set-ID mode-bit rules:** rejects `S_ISUID` (`0o4000`) or `S_ISGID` (`0o2000`) on `chmod`, `fchmod`, `fchmodat`, `fchmodat2`, `mkdir`, `mkdirat`, `mknod`, `mknodat`, `creat`, `open` and `openat` (when `O_CREAT` or architecture-specific `O_TMPFILE` is set in `flags` and `O_PATH` is not set — Linux `build_open_flags()` discards creation flags with `O_PATH`), and `mq_open` (when `O_CREAT` is set in `oflag`), per target architecture (`x86_64` including `x32` syscall numbers, `aarch64`, and `riscv64`; `msgget`, `semget`, and `shmget` are intentionally not filtered because the Linux kernel masks `ipc_perm.mode` to `0o777` and `0o2000`/`0o4000` are valid `IPC_EXCL`/`IPC_NOWAIT`/`SHM_HUGETLB` flags).
    2. **`io_uring` denial in both `Standard` and `Strict`:** unconditionally denies `io_uring_setup` (425), `io_uring_enter` (426), and `io_uring_register` (427) on all architectures (including `x32`), because a ring lets a process submit `IORING_OP_OPENAT`, `IORING_OP_OPENAT2`, and `IORING_OP_MKDIRAT` inside the kernel past every scalar seccomp check (and MiraServe's standing policy keeps `io_uring` blocked). Nothing in MiraServe or its dependencies uses `io_uring` (`tokio` is built without its `io-uring` feature; `wasmtime`, `rustls`, `hyper`, and `quinn` make zero `io_uring` calls). **Embedder impact:** an embedder that previously relied on `SeccompMode::Standard` permitting `io_uring` loses ring access in `Standard` (`EPERM` on all three syscalls) and must either avoid `io_uring` or run under `SeccompMode::Off` (which disables all seccomp filtering).
    Setting `server.sandbox.seccomp "off"` (warning `W003`) or passing `--no-sandbox` (startup warning) installs **no** seccomp-bpf filter at all — neither the dangerous-syscall denylist nor the in-process set-ID policy — so operators must never pair `seccomp "off"` or `--no-sandbox` with a unit that omits `RestrictSUIDSGID=yes`.
  - **Service unit opt-in and startup/`check` probe (`miraserve service generate`, `miraserve check`, `miraserve run`):** `packaging/systemd/miraserve.service`, the default output of `miraserve service generate --target systemd`, and `miraserve service generate --target systemd-keyd` keep `RestrictSUIDSGID=yes` unchanged. Passing `--allow-openat2` to `miraserve service generate --target systemd` omits `RestrictSUIDSGID=yes` from the worker unit (with an explanatory comment) so Linux `openat2(2)` works for single-call whole-path lookups, `file-cache` admission, inline worker-loop lookups, and in-task HTTP/2 static serving. Note that on **systemd 258+**, `/etc/systemd/system.conf` can set `DefaultRestrictSUIDSGID=yes`, which applies `RestrictSUIDSGID=yes` even when a unit omits the line (operators opting in on such hosts need a unit drop-in setting `RestrictSUIDSGID=no`). When a configuration enables `file-cache` (with `server.limits.file-cache-bytes > 0`), sets `server.workers` to anything other than `"shared"`, or configures an HTTP/2 listener with effective static file work on Linux **5.12–6.11** (using the pre-sandbox cached kernel release, the compiled router's `has_static_work()` at startup, and the classified config in `miraserve check --fs` so quarantined tenant sites do not trigger a probe), `miraserve check` and startup run a side-effect-free probe (`openat2(AT_FDCWD, "", O_RDONLY | O_CLOEXEC, 0, 0)`, which returns `ENOENT` when allowed; followed by `openat2(..., RESOLVE_CACHED)` when plain `openat2` succeeds) and emit a single notice on a recognised refusal (`ENOSYS`, `EPERM`, or `EACCES`) or on `EINVAL` for `RESOLVE_CACHED` (Linux 5.6–5.11 when `workers` is enabled). At runtime startup, that notice is logged at `WARN` only when the loaded configuration asks for a feature degraded by the refusal (a site with `file-cache` other than `"off"` while `server.limits.file-cache-bytes` is non-zero, or `server.workers` other than `"shared"`) and at `INFO` otherwise (identical message text; the `"HTTP/2 stream execution mode selected"` `INFO` line is unchanged), while `miraserve check` keeps emitting it as a plain informational note (no warning code). Configurations where none of those features apply (including HTTP/1.1-only proxies, HTTP/2 proxy-only configs with no static work, and HTTP/2 proxies whose only static tenant was quarantined) issue **no** `openat2` probe at startup or in `miraserve check --fs`:
    - The seccomp-active check reads `/proc/thread-self/status` (`Seccomp:` field of the **probing thread**, not `/proc/self/status` of the thread-group leader). When `ENOSYS` occurs with `Seccomp: 0` on the probing thread, the notice reports a pre-5.6 kernel and states that regenerating the unit cannot help (and still emits the disabled-policy warning below when in-process seccomp is not active). When a filter is active (`Seccomp: 1` or `2`) or for `EPERM`/`EACCES`, the notice names the applicable causes and remedies (systemd `RestrictSUIDSGID=yes` / `DefaultRestrictSUIDSGID=yes`, an outer container seccomp profile, or a pre-5.6 kernel).
    - At runtime, the notice inspects the **installed** `SandboxReport` (accounting for `--no-sandbox` as well as embedders supplying a prebuilt `SandboxPolicy`, rather than assuming `config.server.sandbox.seccomp`). Whenever in-process seccomp is not active (`seccomp "off"`, `--no-sandbox`, or a prebuilt policy with seccomp disabled), the notice refuses to recommend removing `RestrictSUIDSGID=yes` and warns that the unit without that line would have **no** set-ID protection. Standalone `miraserve check` cannot see an `ExecStart ... --no-sandbox` override in a unit file, so its regeneration advice explicitly instructs the operator to confirm the effective worker `ExecStart` command keeps in-process seccomp active.
    - **Scope and probe caveats:** `miraserve check` run from an interactive shell observes the **shell's** seccomp policy, whereas `ExecStartPre` runs inside the systemd unit and observes the **unit's** policy. **Silence (`None`, no advisory) means only "no recognised refusal"** — an outer filter returning an unrecognised errno (for example a filter-supplied `EINVAL` on plain `openat2`) also produces no advisory. If an outer seccomp policy denies `openat2` with a kill action instead of returning an errno, `SECCOMP_RET_KILL_PROCESS` terminates the entire process with `SIGSYS` (including `miraserve check` or `miraserve run` when an affected feature triggers the probe), whereas `SECCOMP_RET_KILL_THREAD` (or legacy `SECCOMP_RET_KILL`) terminates only the probing thread with `SIGSYS` and can leave other startup threads alive in a multi-threaded process; configurations without static work or without HTTP/2/`file-cache`/`workers` never call the probe and survive a kill-on-`openat2` policy cleanly. When plain `openat2(2)` succeeds, the follow-up `openat2(RESOLVE_CACHED)` probe distinguishes Linux 5.6–5.11 (`EINVAL`, advising kernel upgrade rather than `--allow-openat2` for `workers`; on Linux 5.9–5.11 HTTP/2 is already excluded from the advisory so `--allow-openat2` is never recommended as enabling in-task HTTP/2 there) from Linux 5.12+ (`ENOENT`).
  - **Residual risk without `RestrictSUIDSGID=yes` (why `--allow-openat2` is opt-in):** MiraServe's in-process policy blocks every scalar set-ID syscall and all three `io_uring` syscalls in both `Standard` and `Strict` modes, but classic seccomp-bpf cannot dereference `openat2(2)`'s userspace `struct open_how` pointer, so it cannot inspect `openat2` calls carrying `O_CREAT` or `O_TMPFILE` and is **not** equivalent to systemd's `RestrictSUIDSGID=yes`. A compromised worker running without `RestrictSUIDSGID=yes` can therefore still call `umask(0)` and `openat2` with `O_CREAT` or `O_TMPFILE` to create a set-ID inode owned by the service user (with the worker's effective group, or the parent directory's group on a set-GID parent, subject to Linux group-membership checks for executable `S_ISGID`) wherever its effective filesystem policy permits it, and can `chmod` service-owned directories and ancestors to make them searchable by other local users (ordinary `chmod` requests no set-ID bit, so our filter allows it, and Landlock does not mediate `chmod`).
    - **Reachable directories under enforcing Landlock (`MakeReg` vs `O_TMPFILE` `WriteFile`) — complete inventory of Landlock write grants:**
      1. **Named regular-file creation (`O_CREAT`, Landlock `AccessFs::MakeReg`):** MiraServe grants full read-write access (`ReadFile | ReadDir | WriteFile | Truncate | MakeReg | MakeDir | RemoveFile | RemoveDir | Refer`, `crates/miraserve-sandbox/src/lib.rs`) only to three directory categories: (a) `--acme-dir` (packaged `/var/lib/miraserve/acme`, `0700 miraserve:miraserve` beneath `/var/lib/miraserve` `0750 miraserve:miraserve` per `packaging/systemd/miraserve.tmpfiles`; writable in `packaging/systemd/miraserve.service` via `StateDirectory=miraserve` and `ReadWritePaths=/var/lib/miraserve`); (b) `ai-publish.storage` if configured (packaged default `/var/lib/miraserve/releases`, `0750 miraserve:miraserve` in `tmpfiles`, writable under `StateDirectory=miraserve` / `ReadWritePaths=/var/lib/miraserve`; custom paths outside `/var/lib/miraserve` are read-only under `ProtectSystem=strict` unless added to `ReadWritePaths=`); and (c) any validated rotating-log parent if `--log-max-bytes > 0` (packaged `/var/log/miraserve`, not in `tmpfiles`, created `0750 miraserve:miraserve` and made writable by `LogsDirectory=miraserve` / `LogsDirectoryMode=0750` in the unit; custom paths require `ReadWritePaths=`).
      2. **Unnamed temporary-file creation (`O_TMPFILE`, Landlock `AccessFs::WriteFile`):** On Linux across every Landlock-capable kernel version we support (verified in `fs/namei.c` `path_openat`/`do_tmpfile`/`vfs_tmpfile` and `security/landlock/fs.c` `hook_file_open`/`landlock_hooks` across Linux 5.13 ABI v1, 5.19 ABI v2, 6.8 ABI v4, 6.10 ABI v5, 6.12 ABI v6, and mainline), `O_TMPFILE` takes a separate VFS path that never calls `security_path_mknod` (`MakeReg`); Landlock checks the resulting open only in `hook_file_open` for `WriteFile` (plus `ReadFile` for `O_RDWR`). Besides the three read-write categories above, MiraServe grants `ReadFile | WriteFile` (without `MakeReg` or `Refer`) to: (d) configured `server.sandbox.socket_trees` (`socket-tree`, validated directories; neither `packaging/systemd/miraserve.service` nor `miraserve.tmpfiles` creates or adds `ReadWritePaths=` for them. Whether the mount is writable is a property of the EFFECTIVE mount, not of the tree being a `socket-tree`: under `ProtectSystem=strict` a tree outside the unit's writable paths (an ordinary `/run/php`) is read-only in the worker's namespace and `O_TMPFILE` there fails with `EROFS`, whereas a tree under `/var/log/miraserve` is writable through `LogsDirectory=miraserve` whether or not log rotation is configured (`/var/lib/miraserve` and `/run/miraserve` are writable too, but the configuration validator refuses a `socket-tree` at or beneath either). (This analysis is about the unit generated with `--allow-openat2`; under the packaged unit the `openat2` call is refused by systemd's filter before any mount check.) Wherever the effective mount is writable, the filesystem implements `->tmpfile`, and ordinary Unix permissions permit `MAY_WRITE | MAY_EXEC`, a `socket-tree` directory admits an unnamed `O_TMPFILE` set-ID inode); and (e) exact Unix socket paths (`server.tls.keyd_socket`, packaged `/run/miraserve-keyd/keyd.sock` inside `tmpfiles` `2750 miraserve-keyd:miraserve` `/run/miraserve-keyd`, and per-route `fastcgi-pass "unix:..."`), which are socket inodes (`S_IFSOCK`, not directories, so `O_TMPFILE` fails with `ENOTDIR`; if misconfigured to point at a non-socket, three outcomes apply: (a) a non-socket whose path spelling is not itself an entry of another grant list (for example, a TLS certificate file such as `/etc/miraserve/certs/site.pem` in a dedicated certificate directory covered only by its parent directory's read-only grant `/etc/miraserve/certs`): no socket rule is installed and one `WARN` is logged, so that entry contributes no write rule and access depends only on any independently covering Landlock grant; (b) a directory whose exact path spelling is itself an entry of another grant list (site or route root, `read-tree`, publish storage, ACME directory, config or certificate parent, or rotating-log directory): the 0.1.5 `ReadFile | WriteFile` socket-class rule is kept and one `WARN` is logged; (c) a non-directory whose exact path spelling is itself an entry of another grant list (for example, an individually granted file such as a TLS certificate file in `split-daemon` mode sharing a directory with its private key, where parent widening is refused and the file path itself enters the read-only grant list, also configured as `fastcgi-pass "unix:..."`): its socket rule is reduced to read access (`AccessFs::ReadFile` only) and one `WARN` is logged). Giving an unnamed `O_TMPFILE` a directory entry (`linkat`) is a separate operation: the inode must be opened without `O_EXCL` (so `I_LINKABLE` is set; unprivileged callers link via `/proc/self/fd/<n>` with `AT_SYMLINK_FOLLOW`; `linkat(AT_EMPTY_PATH)` needs `CAP_DAC_READ_SEARCH` up to Linux 6.9 and from Linux 6.10 is also accepted when the caller's credentials match those the file was opened with; Landlock's checks apply either way), and Landlock's `hook_path_link` requires `MakeReg` on the destination directory for same-directory linking — plus `Refer` on both source and destination parents, `MakeReg`, and a destination restriction superset for cross-directory linking on Landlock ABI v2+ (Linux 5.19+), or returns `EXDEV` unconditionally on ABI v1 (Linux 5.13–5.18). A `socket-tree` grant ALONE therefore gives no right to name the inode. But the grants of one Landlock ruleset add up: a `socket-tree` that lies beneath a directory with a read-write grant (the validator accepts one under a rotating-log parent such as `/var/log/miraserve`) inherits that grant's `MakeReg`, and a same-directory `linkat` then succeeds if the ordinary filesystem checks pass; the overlapping grants, not the `socket-tree` setting, decide. In every case an open descriptor to an unnamed inode can still be passed over a Unix socket (`SCM_RIGHTS`) and executed via `execveat(AT_EMPTY_PATH)`; on a `nosuid` mount that execution can still succeed, but it confers no set-ID credentials (`nosuid` suppresses the credential change, not the execution).
      3. **Paths without Landlock write grants, and behavior without Landlock:** Document roots, config, certs, and `read-tree` paths receive read-only Landlock grants (`ReadFile | ReadDir` only); `/run/miraserve` (`0750 miraserve:miraserve` in `tmpfiles` and `RuntimeDirectory=miraserve`/`ReadWritePaths=` in the unit), `/var/lib/miraserve` itself (parent of `acme`/`releases`), `PrivateTmp` (`/tmp`, `/var/tmp`), and `/dev/shm` receive no Landlock grant at all. **Without** enforcing Landlock, the reachable writable set expands to whatever the systemd unit and ordinary filesystem permissions leave writable (under the generated unit: `/var/lib/miraserve`, `/run/miraserve`, `/var/log/miraserve`, service-private `/tmp` and `/var/tmp` under `PrivateTmp=yes`, `/dev/shm` which stays writable under `PrivateDevices=yes`, and any custom `ReadWritePaths=` / `--acme-dir`).
    - **What does and does not bound the residual:** `NoNewPrivileges=yes` and `seccomp "strict"`'s `execve`/`execveat` denial protect **the worker side only** (another local host process has its own credentials and mount namespace, and service-private `NoExecPaths=` does not govern it). **Directory modes on service-owned directories (`0700`/`0750`) are NOT a control against a compromised worker**, because the worker owns those directories and can `chmod` them. **Pathname control vs credential guarantee (not alternatives):** a **root-controlled, non-searchable ancestor directory** is a **pathname control only** — it blocks pathname traversal by other local users, but does **not** stop an independent process that is handed an open file descriptor to the inode (for example via `SCM_RIGHTS` fd passing over a Unix socket the worker may use, followed by `execveat(AT_EMPTY_PATH)`). The **credential guarantee** is **`nosuid` on every mount through which the inode can be executed**, which suppresses the set-ID credential change on execution even when an open descriptor is passed. Additional bounds: the unit grants no `CAP_CHOWN` (only `CAP_NET_BIND_SERVICE`), so the inode cannot be made `root`-owned; ordinary unprivileged writes can clear set-ID bits on Linux. If a usable marked executable survives and another local process executes it through a non-`nosuid` mount, the effective UID and effective GID it may gain (a process that itself runs with `no_new_privs` gains none) depend **separately** on which executable set-ID bit survives: executable `S_ISUID` may confer the file owner's UID (`miraserve`), while executable `S_ISGID` with group execute may confer the file's group (`miraserve` or a supplementary/parent group), exposing the files accessible to that UID or GID — including worker-owned TLS certificates/keys, ACME account material in `--acme-dir`, `ai-publish` storage, and group-readable config/auth files. Note that switching to split `miraserve-keyd` isolates `keyd`'s own TLS signing keys (under `/etc/miraserve/keys`, `0700 miraserve-keyd:miraserve-keyd`) and disables built-in ACME issuance (`E106` if sites still rely on ACME), but **leaves any existing worker-owned ACME account material in `--acme-dir` in place** until removed by the operator. Because closing this gap requires host-level `nosuid` mounts (and, for pathname confinement, root-controlled ancestors) outside the unit, `--allow-openat2` remains an explicit opt-in while the packaged and default generated units retain `RestrictSUIDSGID=yes`.
- **Writable-set CLI policy reports (`miraserve check --writable-set`, `miraserve service generate --target systemd ... --print-writable-set`, 0.1.5):** Policy-reporting commands for installers and hosting panels deciding whether to opt into `--allow-openat2`. They report MiraServe's own policy and unit directives only — **never a host mount attestation**. Both machine-readable modes propagate write and flush errors on the report's stdout and exit non-zero on truncated output (a failed write of a diagnostic to stderr does not change the exit status).
  - **`miraserve check --writable-set <config>` (Landlock policy report, superset rule):** Accepts the same grant-affecting flags as `miraserve run` (`--acme-dir`, `--log-file`, `--access-log`, `--log-max-bytes`, `--keyd-auth-secret-file`, `--no-sandbox`) and **must be invoked with the exact same options, working directory (relative log destinations and default `.miraserve-acme` depend on the service's working directory), user, and `LimitNOFILE` as the service's `ExecStart`**. Validates `<config>` identically to plain `miraserve check` (preserving validation exit status and stderr diagnostics, except that control characters in diagnostics are escaped and a config path that contains control characters is refused before it is read; incompatible with `--format json` and `--dump-normalized`), rejecting control characters in path-valued CLI options (the positional config path, `--acme-dir`, `--log-file`, `--access-log`, and `--keyd-auth-secret-file`) and writable-candidate config paths, and routing every line emitted by the command handler to stderr and stdout through a single sanitising writer that escapes all C0, DEL, and C1 control characters (argument-parser errors for malformed flag values are printed directly by the CLI argument parser before the command handler runs). On validation success, drops the preliminary warning-only policy before running its inspection startup classification and policy preparation pass (mirroring `miraserve run`'s quarantine, policy, and CLI log-binding steps without creating directories, opening log files, or installing any Landlock ruleset or `PR_SET_NO_NEW_PRIVS`), validates the effective `--acme-dir` unconditionally using its forbidden-directory check and side-effect-free no-follow, ancestor-safety, and ownership checks (on Unix; on other platforms only the type of the directory itself is checked) (refusing forbidden directories such as `/etc` with the inspection's own diagnostic, and refusing symlinked leaves/ancestors, unsafe ancestors, or wrong ownership), and prints line-oriented records to stdout:
    1. Exactly one Landlock state line first — a **capability prediction** only (an outer policy such as seccomp or another LSM can still deny `landlock_restrict_self`, in which case `run` fails closed; the line says nothing about seccomp):
       - `landlock enforced abi=<n>` — Linux kernel reports Landlock ABI `>= 5` (MiraServe's target ABI, Linux 6.10+) and `run` will request full ruleset enforcement.
       - `landlock partial abi=<n>` — Linux kernel reports Landlock ABI `1..4` and `run` will request partial ruleset enforcement. **Important ABI 1–2 caveat:** on ABI `1` (Linux 5.13–5.18), cross-directory rename/link is **denied** (`EXDEV`; ABI `2` added `AccessFs::Refer` to allow it), and on ABI `1`–`2` (Linux 5.13–6.1), `AccessFs::Truncate` does not exist in the kernel so Landlock does **not** restrict file truncation (`truncate(2)`, `ftruncate(2)`, `O_TRUNC`); on ABI `3`–`4` (Linux 6.2–6.9), truncation is enforced and only ABI `5` device `ioctl` filtering is absent.
       - `landlock disabled` — Linux host where Landlock is switched off (`sandbox { landlock #false }` or `--no-sandbox`); no kernel ABI probe is performed.
       - `landlock unavailable` — non-Linux platform (always `landlock unavailable` regardless of `sandbox { landlock ... }` or `--no-sandbox`), or a Linux kernel without Landlock support.
    2. When Landlock is predicted to enforce (`enforced` or `partial`), candidate writable paths following the **superset rule** — the report may name a path that `run` in the end does not grant, and never omits one that `run` can grant, including directories that startup itself creates (such as an absent `socket-tree` created by a non-rotating log parent, absent Unix sockets, or candidate writable paths of any site quarantined during classification); no candidate is dropped silently and no permission inference (`accessat`) is made from the inspecting account:
       - `writable landlock <path>` — existing filesystem object (such as a writable directory, socket, or—under the superset rule—an existing non-socket object at a configured exact socket path that the installer later skips) pinned by the policy; on Linux the printed path is derived from the pinned `O_PATH` descriptor (`/proc/self/fd/<fd>`) and verified for exact `(st_dev, st_ino)` identity match. If `/proc/self/fd` is unavailable or the pinned descriptor's name lookup cannot be resolved (or mismatches/unlinks), **the command fails** (non-zero exit, empty stdout) — an unresolvable name lookup on a pinned descriptor is an inspection failure, not a `writable-missing` record. This is a **point-in-time snapshot**: a rename after the command exits is outside the contract.
       - `writable-missing landlock <absolute lexical path>` — strictly for absent or unopenable candidate writable grants (`--acme-dir`, `ai-publish.storage`, rotating-log parent, `socket-tree`, or Unix socket path — e.g. `ENOENT`, `EACCES`, `ELOOP`, `ENOTDIR`) and candidate writable paths of sites quarantined during classification.
       Exit status `0` with only the state line means Landlock would ask for no writable grants. When Landlock is `disabled` or `unavailable`, no writable records are emitted. Genuine hard rejections — unsafe non-tenant docroot, rotating-log overlap (when the overlapped document root belongs to an `owner-dir` tenant, that tenant can be quarantined instead and the inspection completes), invalid or forbidden `--acme-dir` such as `/etc` (refused with the inspection's own diagnostic), forbidden `read-tree`/`socket-tree`, a forbidden `ai-publish.storage` target (including a symlink to a forbidden directory) on a site that is **not** quarantined (a quarantined site's forbidden store target gets no grant and may produce no diagnostic), pin identity mismatch, unavailable `/proc/self/fd` name lookup, non-UTF-8, or control characters in writable paths or path-valued CLI options — exit non-zero with empty stdout and a sanitized stderr diagnostic. **Resource failures (`EMFILE`/`ENFILE`/`ENOMEM`):** the report never omits a candidate writable path because of a resource failure it detects; a detected resource failure while building the reported policy fails the inspection (non-zero exit, empty stdout). Inspection may also fail under a low descriptor limit where `miraserve run` would succeed (because attribution builds a temporary per-site policy while the primary policy is live); run the inspection with the service's `LimitNOFILE`.
  - **`miraserve service generate --target systemd ... --print-writable-set` (unit directive report, no host scanning):** Supported for `--target systemd` and `--target systemd-keyd`, refused for `launchd`/`windows`, incompatible with `--output`/`--tmpfiles-output`. Takes the report branch before reading `--config` for `TimeoutStopSec`/`ProtectHome` inference (so a FIFO `--config` does not block it), and routes every stdout and stderr line emitted by the command handler through the C0/DEL/C1 sanitising writer (argument-parser errors for malformed flag values are printed directly by the CLI argument parser).
    - **Report-mode path validation (`--print-writable-set` only; plain generation is unaffected):** Plain `miraserve service generate` (without `--print-writable-set`, across every target) runs the same validation and rendering as before the report mode existed (every input 0.1.4 accepted is accepted and rendered as in 0.1.4) and calls none of the report's path validators. When `--print-writable-set` is given, the report refuses path spellings it cannot represent exactly, including some systemd would normalise, such as a trailing slash (`/var/lib/miraserve/acme/`), `.` segments, or duplicate slashes (`//`), and also `..` segments (which systemd refuses as well), exiting non-zero with empty stdout and a sanitized stderr diagnostic; plain generation is unaffected. Specifically, in `--print-writable-set` mode: fields rendered only through `systemd_quote` (`--binary`, `--config`, `--auth-secret-file`, and the full `--keyd-socket` endpoint in `ExecStart`) accept spaces as in 0.1.4; `--acme-dir` on `--target systemd` is quoted in every directive (`ExecStart*` and `ReadWritePaths=-"..."`) so it uses the quoted normalized-absolute-path grammar (accepting spaced normalized paths such as `"/var/lib/custom acme/state"` while refusing relative paths, `/`, trailing or duplicate slashes, and `.`/`..` segments); the strict unquoted systemd/tmpfiles path grammar (additionally refusing whitespace including non-ASCII whitespace, quotes `"`, `'`, backslashes `\`, and glob metacharacters `*`, `?`, `[`, `]`) applies **only** to the **parent directory** of Unix `--keyd-socket` on `--target systemd-keyd` (so a space confined to the keyd socket filename under a clean parent such as `"/run/miraserve-keyd/signer A.sock"` is accepted), and Unix `--keyd-socket` must name a socket file (not `.`/`..`/trailing `/`) whose parent directory is not `/`, `/run`, or `/var/run` (the operator must still dedicate the chosen parent directory to keyd because `tmpfiles.d` applies mode `2750` and the ownership of the keyd service account, `--user`, default `miraserve-keyd`, to it); loopback `tcp://127.0.0.1:<port>` / `tcp://[::1]:<port>` is validated with `KeydEndpoint::parse` without whitespace, quotes, or backslashes.
    - Emits **only the directives the rendered unit contains** (derived directly from the same `SystemdUnitFsSpec` that renders the unit — **nothing verified on the host, zero host filesystem scanning**):
      - `writable unit <path>` — sorted, deduplicated literal paths from `StateDirectory` (`/var/lib/<name>`), `RuntimeDirectory` (`/run/<name>`), `LogsDirectory` (`/var/log/<name>`), and `ReadWritePaths` (unused `--log-dir` on `--target systemd` is omitted; the default main worker unit does not list `/run/php`, though passing `--acme-dir /run/php` explicitly adds it to `ReadWritePaths=`).
      - `writable unit-private-tmp /tmp` and `writable unit-private-tmp /var/tmp` when `PrivateTmp=yes` (two separate records).
  - **Record grammar (stable for 0.1.x) and installer mount-verification responsibilities:** One record per line; fields separated by a single ASCII space; the path is everything after the second space (paths may contain spaces in Landlock records). Record prefixes are `landlock <state>`, `writable landlock `, `writable-missing landlock `, `writable unit `, and `writable unit-private-tmp `. Nothing in these commands inspects or attests to host or service mounts. Before opting into `--allow-openat2`, the **installer** remains responsible for verifying mount options (`nosuid`) outside these commands (the notes below are requirements, not a claim of a complete procedure):
    1. **Inspect in the service's mount namespace, not the installer's:** bind mounts, overmounts, `PrivateTmp=yes`, `PrivateDevices=yes`, and other unit mount directives mean the service's mount tree can differ from the installer's shell.
    2. **Check at and below every reported path, through every bind alias of it, including child filesystems with a different device number (`MAJ:MIN`):** a grant root's own mount options do not cover separately mounted descendants below it, nor descendants reachable uniquely through a bind alias exposing the same underlying filesystem.
    3. **Treat every `writable-missing ...` path as unverified:** fail closed, or provision the missing target first (create a missing directory, or let its producer — such as PHP-FPM or `miraserve-keyd` — provision an exact socket path) and re-run (`findmnt -T "$P"` on `util-linux 2.38.1` prints nothing and exits `1` on absent paths).
    4. **`PrivateTmp=yes` backing:** `PrivateTmp=yes` provides service-private `/tmp` and `/var/tmp` whose backing differs from the host's (it is **not** a `tmpfs` guarantee; systemd normally bind-mounts service-private directories from the underlying `/tmp` or `/var/tmp` filesystem).
    5. **Without Landlock, include `/dev/shm`:** `PrivateDevices=yes` leaves `/dev/shm` writable inside the service's namespace, so `/dev/shm` belongs in the writable inventory whenever Landlock is not enforcing.
    6. **Decode escaped mount paths before comparing:** `findmnt -r` uses **hexadecimal** `\xHH` escapes (for example `\x20` for space), whereas Linux kernel `/proc/self/mountinfo` uses **octal** `\NNN` escapes (for example `\040` for space); decode escaped output before comparing against literal paths.
    7. **Account for snapshots and working directory:** `writable landlock` paths are a point-in-time snapshot (a later rename is outside the contract), and relative log destinations (plus default `.miraserve-acme`) resolve against the service's working directory.
- **FastCGI Unix socket access check (`miraserve check --fs`, warning `W033`):** On Unix platforms, `miraserve check --fs` checks each non-quarantined site's `fastcgi-pass "unix:<path>"` without calling `connect()`: the socket must be reachable (search permission on its parent directories) and requires read and write permission on the socket for the account running the check (`uid/gid`). If `metadata` on the configured path fails with `EACCES` (an unsearchable parent directory), `check --fs` emits warning `W033` reporting that the path could not be reached (type and owner unknown) — including when running as `root` or with differing real/effective IDs; `ENOENT` and every other `metadata` error produce no output. When the path exists and is a Unix domain socket (`S_IFSOCK`): if the checking process's real and effective UID and GID are equal and non-root, it runs the classic `faccessat(..., R_OK | W_OK, 0)` check (never `AT_EACCESS` / `faccessat2`); on `EACCES` it emits warning `W033` naming the site, socket path, socket owner/group/mode, and checking `uid/gid`, stating that it requires read and write permission on the socket for the account running the check and advising to set `listen.group` of the pool to the server's group or add the server account to the socket's group. Any other error from `faccessat` (`ENOSYS`, `EPERM`, `EINVAL`, ...) is treated as indeterminate (no `W033`, one plain note naming the error). When real and effective UID or GID differ, the check is likewise indeterminate (no `W033`, one plain note that access could not be tested because the real and effective IDs differ); with `uid = euid = 0` and differing real and effective GIDs, the differing-IDs note wins and the root note is not emitted. When running as `root` (`uid = euid = 0` with equal real and effective GIDs) with at least one existing FastCGI Unix socket, it emits no `W033` warning and prints one plain note per run that socket access for the service account was not tested because the check runs as root. `--strict` fails on `W033`, `--allow-warning W033` accepts it, JSON output (`--format json`) carries `W033` in `warnings` and the root/indeterminate notes in `notes` on both valid and failed runs, text mode prints the root and indeterminate notes once each on stdout on successful runs unless `--quiet` or `--writable-set` is passed (including before the normalized JSON when `--dump-normalized` is passed without `--quiet`) and on stderr after warnings on failed `--fs`/`--strict` runs (even with `--quiet`, though omitted on a late `--writable-set` inspection failure), and `miraserve reload --config` (which pre-validates with `--fs` without `--strict`) still succeeds on warnings. The `W033` entry's `path` is `"site[N].route[M].fastcgi-pass"`. Existing non-socket paths give no `W033` and no root/indeterminate notes; absent socket paths, TCP FastCGI targets, `check` without `--fs`, and non-Unix platforms produce no `W033` output or notes.
- **Linux exact Unix socket typing (0.1.6):** On Linux only, when Landlock rules are assembled, an installed socket-class entry whose descriptor is a real Unix socket (or an explicitly configured `socket-tree` directory) is granted `AccessFs::ReadFile | AccessFs::WriteFile` quietly. For an installed socket-class entry that is not an explicitly configured `socket-tree` directory and whose descriptor is not a socket, three outcomes apply: (a) a non-socket whose path spelling is not itself an entry of another grant list (for example, a TLS certificate file such as `/etc/miraserve/certs/site.pem` in a dedicated certificate directory covered only by its parent directory's read-only grant `/etc/miraserve/certs`): no socket rule is installed and one `WARN` per path per process is logged naming the path and type found; the site keeps running while FastCGI or `keyd` requests to that path fail while it is not a socket (an active split-daemon server still requires its `keyd` socket); (b) a directory whose exact path spelling is itself an entry of another grant list (site or route root, `read-tree`, publish storage, ACME directory, config or certificate parent, or rotating-log directory — where for a rotating-log directory bound after initial precedence the 0.1.5 socket-class rule on the replacement descriptor is followed by the pinned read-write rule): the 0.1.5 socket-class rule (`AccessFs::ReadFile | AccessFs::WriteFile`, without `ReadDir`) is kept and one `WARN` per path per process is logged advising the operator to give the socket its own path; (c) a non-directory whose exact path spelling is itself an entry of another grant list (for example, an individually granted file such as a TLS certificate file in `split-daemon` mode sharing a directory with its private key, where parent widening is refused and the file path itself enters the read-only grant list, also configured as `fastcgi-pass "unix:..."`): its socket rule is reduced to read access (`AccessFs::ReadFile` only) and one `WARN` per path per process is logged advising the operator to give the socket its own path. This behaviour is Linux-only; start-up quarantine, missing-socket notices, and `miraserve check` / `--fs` / `--writable-set` output are unchanged from 0.1.5.
- **Extensionless `try-files` fallback (`fallback-unless-extension`, 0.1.6):** A `try-files` directive (route-level, wherever `try-files` is accepted) accepts an optional boolean property `fallback-unless-extension=#true|#false` (default `#false`, preserving 0.1.5 behaviour and `--dump-normalized` plain-array output byte-for-byte; `miraserve check` rejects non-boolean values with `E004`, unknown properties with `E003`, and duplicate properties with `E005`). When `#true`, the **last** candidate in the list — whatever it is, including static shells such as `"/index.html"`, status codes such as `"=410"`, or script/FastCGI fallbacks such as `"/index.php?{query}"` — is evaluated only when the normalised request path (after MiraServe's own path normalisation, without the query string), with at most one trailing `'\n'` (U+000A) removed, does **not** end with a dot followed by 1 to 8 ASCII letters or digits (matching Nginx's PCRE pattern `\.[A-Za-z0-9]{1,8}$`, where `$` also matches immediately before a single final line feed: `/missing.js%0A` is refused and answers `404`, while `/missing.js%0A%0A` and `/missing.js%0D` do not match and use the fallback). Earlier candidates still run as usual (so any existing file or directory/index is served as today whatever its name, and on `GET`/`HEAD` an earlier `=status` candidate such as `"=410"` is still evaluated before the last candidate is reached); when no earlier candidate matches and the final candidate is refused (including on a single-candidate list, which is accepted and means no fallback for extension-like paths), the route answers its own `404 Not Found` — the originating route's not-found answer, with its `headers` rules, `security-headers` policy, and `site.error-pages` — full stop. Refusing the fallback does **not** emulate removing the last candidate from the list: a penultimate non-file candidate never acquires final-candidate internal-rewrite semantics, and on non-`GET`/`HEAD` methods (where earlier `=status` candidates such as `"=410"` are not evaluated before the final candidate) refusing the final candidate answers `404`. Fallbacks that do run preserve 0.1.4/0.1.5 fallback header-rule ownership. With opt-in `file-cache`, `fallback-unless-extension` is isolated in its own cache namespace and a path refused the fallback is never answered from a cached fallback entry and never creates one.
- **Opt-in trusted-path diagnostic (`miraserve check --fs --trusted-paths`, warning `W034`, Linux only):** With `--fs --trusted-paths`, on Linux, `check` walks the directories on the way to covered configured paths and stops at the first component it reports or does not find: `server.sandbox` `socket-tree` roots (`server.sandbox.socket-tree`), exact `fastcgi-pass` Unix sockets (`site[N].route[M].fastcgi-pass`), `server.tls.keyd-socket` (the path of the endpoint the server connects to), the ACME directory (`server.tls.acme`, from `--acme-dir` or default `.miraserve-acme`), and rotating log parent directories when `--log-max-bytes > 0` (`--log-file` as `server.log-file`, `--access-log` as `server.access-log`; CLI-sourced paths have no KDL source location). On Linux, `miraserve check --fs --trusted-paths` also inspects the configured `ai-publish.storage` directory (`site[N].ai-publish.storage`) for each site that specifies one. It uses the storage path from the loaded configuration. It reports W034 for a missing store directory, an ownership or mode problem found by the directory walk, or a path it could not verify. The inspection stops at the store directory. Files and directories below it, service write access, and the integrity of published content are outside this check. Other configured paths are not looked at yet. For each path it considers untrusted or cannot verify, it reports warning `W034`; the warning text gives the component (when a component is reported), its owner and mode (when known), and the reason. A warning means the check found something to fix on that path, or could not verify it; the reason in the warning says which, and the usual fixes are to correct the ownership, mode or type of the named component, or to move the path. No warning is not a guarantee. The check sees the filesystem as the checking process sees it. It assumes: the server runs with the same root directory and mount view as the check (the packaged unit gives the server a private `/tmp` and a restricted view of `/home`, so paths there are not covered); ordinary local filesystems without identity mapping, stacking, encryption that hides names, or another writable view of the same directories; nothing changes mounts during the check; no other process shares the service account. Run it as the service account (as the unit `ExecStartPre` does), or as root with `server.sandbox.user` set; when no service account is configured, the check trusts the account that runs it (only root when run as root), so run it as the service account. It is opt-in, reports only, and does not change what the server does. With the flag, the listed path classes are walked and `W034` can be reported, while the existing `--fs` probes still run as before (they are described where they are documented today); nothing else is affected by the flag. It can wait on an unresponsive network or userspace filesystem, like the other `--fs` probes. It writes nothing to the configured paths and does not read their contents; reading a symbolic link can update its access time; it reads a few system files to learn the uid mapping and symlink protection setting, and the account database when `server.sandbox.user` is a name.
- **Linux Landlock availability probe (`miraserve check --fs`, warning `W035`, Linux only):** With `--fs` on Linux, when `server.sandbox.landlock` is enabled (and `--no-sandbox` is not passed), a `check` that reaches this probe makes one query-only `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)` version query (without creating or enforcing a ruleset, setting `PR_SET_NO_NEW_PRIVS`, restricting the checking process, or opening any configured path; when `--writable-set` is also passed, the same query result is reused so at most one query is made per invocation, and compared with `0.1.6` this single version query is an accepted system-call difference for `check --fs` with Landlock enabled on Linux). `W035` (`path`: `"server.sandbox.landlock"`, counted by `--strict` and accepted by `--allow-warning W035`) reports one thing: that this version query in the checking process could not confirm Landlock at or above the required ABI (`1`) (not available, disabled, query refused, or ABI too low), noting that `miraserve run` refuses to start when Landlock is unavailable. `W035` is omitted when the version query reports an ABI at or above the required minimum, when `server.sandbox.landlock` is `#false` or `--no-sandbox` is passed, without `--fs`, or on non-Linux platforms. Absence of `W035` is not a guarantee that `miraserve run` will start (for example, a filter that refuses the later restriction step is not detected); the check reflects the environment of the checking process, which can differ from the service.
- **Capability discovery (`miraserve version`, 0.1.4):** `miraserve version` emits a `features:` line listing comma-separated supported capability tokens (`features: precompressed, header-rule-status, service-allow-openat2, writable-set, try-files-extensionless` — 0.1.5 adds `service-allow-openat2` and `writable-set`, and 0.1.6 appends `try-files-extensionless`, preserving token order by appending) so hosting panels and automation can probe supported directives and options directly, without parsing `--help` or version numbers.
